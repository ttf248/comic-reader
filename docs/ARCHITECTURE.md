# 系统架构

本文维护当前模块入口、数据流与修改时必须守住的边界。接口字段见 [API.md](./API.md)，界面及开放问题见 [DESIGN.md](./DESIGN.md)，运行与验证命令见根 [README.md](../README.md)。

## 模块与依赖

系统是单 Go 进程、本地媒体文件、JSON 状态与浏览器 UI。开发由 Vite 代理 API，生产由 Fiber 单端口提供 API 和前端静态文件。

```text
React routes/components → api + TanStack Query（服务端状态）
                       → Zustand（客户端状态）
        │ 资源 ID / JSON / SSE
        ▼
Fiber middleware → handlers → services/store → models + 本地文件
```

## 资源快照与安全边界

`ResourceCatalog` 是绝对路径转换为公共 ID 的唯一组件。`r_`、`a_`、`c_`、`f_` 分别代表根、相册、集合和文件；由根标识、资源类型与相对路径派生，路径不变时稳定，不可逆推出完整路径。

发布时构建 raw 扫描结果、ID 表、manifest、目录直属子项、全局相册、媒体自然顺序、标签与搜索索引，集合统计聚合全部后代。结果与索引通过一次原子指针更新发布为同一 revision，分页请求不重新遍历目录树。

每个请求只 Acquire 一次 `CatalogSnapshot`，资源参数中间件把快照固定到 Fiber Locals，handler 沿用同一版本。分页游标绑定 revision 和作用域，重扫后的过期游标由客户端丢弃已合并页面后重新读取，具体错误见 API。作用域是全等比较的字符串，列表作用域带内容属性段（`library-children:<父 id>:<属性>`、`library-unread:<属性>` 等），跨属性复用旧游标会被拒绝为 `invalid_cursor`。

请求先过 `AccessGate`，再解析资源与校验路径。门禁检查 Host、Origin / Fetch Metadata、local/LAN 认证；配置与目录管理再加回环限制。LAN SSE 使用 HttpOnly 同源会话，不把令牌放 URL；会话驻留内存，令牌轮换使旧会话失效。当前服务不终止 TLS，使用边界是本机或可信家庭网络。

ID 只能证明扫描时的身份。每次媒体、批量元数据及系统打开请求仍通过共用 `PathValidator` 按当前根校验：

- 用最具体的配置根授权，与根顺序无关；显式链接根允许作为边界，根内未单独配置的符号链接/junction 拒绝，失败不回退到更宽的父根。
- 逐级检查扫描后替换的链接，文件资源须仍是普通文件，目录资源须仍是目录；失效先于 ETag、Range、派生缓存及发送，不产生暴露路径的目录重定向。
- 绝对路径只保留在后端及受回环限制的配置管理交互中；日志、公共错误与媒体响应只给别名、相对路径或稳定 ID。

这不提供针对受信本机进程任意并发改写文件系统的事务隔离。配置文件含本机路径与令牌，Unix 加载/写入收紧为 `0600`，Windows 使用仅授权当前用户的受保护 DACL，失败则拒绝加载或保存。

## 扫描与库发布

1. `NormalizeRoots` 相对 CWD 绝对化、去空并保序去重；Windows 忽略大小写，其他平台区分大小写。规范化不读取目录、不解析链接，离线根仍可用于配置和缓存等价比较。
2. `StartOrReuse` 全局复用一个活动扫描，记录根身份与可读性；每个根读取前后、整理后及提交前复核，空根合法。根消失、不可读、被替换则整轮失败，保留已发布快照与磁盘缓存。
3. Scanner 使用 `min(8, NumCPU)` 个固定目录 worker，协调器派发子目录、worker 返回记录，枚举后建树，不递归占用令牌等待子任务。每个根的子 context 在成功、失败或取消时关闭并等待全部 worker。
4. 父根遇到单独配置的子根时委派给子根，归属取最具体根，不重复统计或增加包装集合；未配置的链接跳过并告警。普通子目录读取失败仅在根仍有效时降为脱敏告警。
5. 构造候选结果并叠加仍有效的自定义封面，验证 scan generation，然后一次发布结果与资源/分页索引；持久化扫描缓存，最后发送带 revision 的 complete。

混合目录生成集合和“本目录媒体”虚拟相册，两者共享真实目录但 kind/ID 不同。虚拟相册的 `name` 是固定类型标记，展示和搜索使用 `location` 相对路径；同名目录不能只靠 basename 区分。目录与媒体自然排序。业务日期由扫描层按 `filename > folder > modified` 解析：`filename` 是从文件名推断的拍摄时间（相机与手机普遍把时间写进文件名），不读 EXIF，因此不引入随机 I/O；前端时间线不重复猜目录日期，“最近改”另外使用 `modTime`。集合也带时间：目录修改时间与后代相册拍摄时间的代表值（按媒体数加权取众数）。

媒体根规范路径或内容属性变化时，配置 handler 串行执行保存、推进 generation、取消旧任务、清库并启动最新根扫描；空根仅清库。旧任务保留登记至回收，但不再被新扫描复用，退出等待新旧任务全部结束。等价根写法和重排不清库或重扫。自定义封面在发布前统一叠加到各引用视图，不能让卡片、详情与标签封面分裂。

### 扫描缓存与 SSE

- `ScanResultCache` 只负责重启恢复与落盘，磁盘含 raw 路径，不作为 HTTP 数据源；schema 版本取 `scanCacheSchemaVersion`，不匹配时隔离并冷启动。恢复比较规范化根 ID 集合，拒绝重复根及实体树中同 kind 的重复路径，允许虚拟相册和集合共享目录、标签重复引用相册。
- 缓存读取用原子指针，更新用 Store/CAS；文件检查移出锁，500ms 防抖落盘，版本号确保 flush 期间的新写入不被误标为已保存。清空与落盘互斥，退出强制 flush。
- SSE 每连接显式订阅并持有释放函数，独立缓冲避免慢客户端阻塞扫描；连接关闭释放订阅与心跳，不取消共享任务。每 15 秒注释心跳，终态或通道关闭结束连接。
- 订阅注册与最新快照取得保持一致，重连恢复原阶段、耗时、数量、进度与 revision。任务终态短期保留后回收，不能重新启动扫描来恢复进度。
- 进度按根与阶段估算且不回退，根读取累计 0–95%、整理 99%，成功发布才为 100%；取消/失败保留最后有效进度与脱敏路径，不发布部分结果。

## 媒体分析任务

`AIJobService` 与扫描任务分开运行：扫描负责发布当前资源快照，分析服务只处理快照内的图片文件。`metadata`（EXIF/GPS）、`embedding`（Chinese-CLIP）、`ocr`（RapidOCR）与 `face`（YuNet + SFace）都通过 `AIAnalyzer` 注册并各自维护版本。全量任务重算全部图片，增量任务按资源 ID、大小、纳秒修改时间与模块版本筛出新增或变化项。人物分析通过 `peopleEnabled` 默认关闭；明确开启后才允许手动、按序或每日启动 `face` 任务。OCR 文本和人脸框/特征写入既有分析批次；相似人脸接口只返回通过当前路径和文件指纹检查的照片 DTO，不对外暴露特征向量。每个结果仍由现有任务服务按 32 张一批提交、恢复与重试，不另设任务队列。

任务状态与每日计划写在 `state/ai_jobs.json`，每 32 张图片提交一个批次检查点；批次结果使用同目录内的原子 JSON 文件，位于 `derived/metadata/<模块>/batches/<任务 ID>/`，可重建且与用户状态分开。结果文件先原子发布，再写检查点；启动时扫描结果批次并修复“结果已写、检查点未写”的崩溃窗口。任务恢复只从最近已提交的批次继续，未提交的尾批会重跑。失败记录写入同一批次，错误仅含资源 ID、稳定错误码和脱敏原因。

「哪些图片已经是最新的」只有一份实现：`aiRecordIsCurrent`（`internal/services/ai_jobs.go`）比对既有结果的大小、纳秒修改时间与模块版本，并交给模块自己的 `RecordCurrent` 校验。任务开跑时筛选候选集用它，空闲时的规模核算也用它 —— 两条路径共用一份判据，预估出来的增量张数才与任务实际的 `planned` 对得上。

空闲时的规模核算由 `AIJobService.Estimate`（`internal/services/ai_job_estimate.go`）提供，经 `GET /api/ai/jobs/estimate` 暴露，只读、不建任务、不写状态文件。文件指纹清单由 8 个 worker 并发采集（stat 是 IO 密集的，与分析 worker 的 4 个上限分开），按媒体库 revision 缓存 30 秒；**任务开跑不复用这份缓存**，它必须用当下真实的 stat，否则文件刚被改过时会被误判成「已经是最新的」而跳过重跑。核算的 IO 全在任务状态锁之外，锁内只做内存里的计数。预计耗时取同模块历史终态任务（`completed` 与 `failed`）每张耗时的中位数，`elapsedMs` 与 `speedPerSecond` 不落盘，耗时由 `startedAt` / `finishedAt` 与实际分析张数重算；没有历史就返回空值，不给默认速度。

每个任务最多使用 4 个 worker；embedding 分析器把 Worker 并发限制为 1，保证同一进程只有一条 GPU 推理请求。暂停在批次边界生效；取消不提交当前未完成批次；退出将运行中任务恢复为 pending，暂停任务保持 paused。启动时自动恢复 pending；活动任务只有一个，断开 SSE 只释放订阅，不影响共享任务。每日增量计划使用服务本机时钟，初始时间为 03:00、默认开启；计划保存模块选择，错过前一计划日后启动时补跑一次，同一天不重复创建。到时按选择顺序把就绪模块的增量任务写入既有 pending 队列，未就绪的模块不启动。

运行中的阶段依次报告 GPU 环境检查（GPU 任务）、媒体库等待、分析清单整理、首批模型准备和模块批量推理；首批推理可能包含 Python 模型冷启动。Worker 按 CPU 与 CUDA 各缓存一份 Chinese-CLIP，进程退出时释放；第一次使用另一种设备仍需加载一次，之后切换复用缓存。GPU OOM 自动回退时丢弃失效的 CUDA 缓存并把当前模型保存为 CPU 实例，避免后续误用不完整的 GPU 状态。任务 ETA 仍基于任务运行墙钟和已完成图片推算，包含首次模型加载及批次提交时间；对于很小的任务会偏粗，阶段标签可以区分准备过程，但 API 还不单独提供模型加载毫秒数。

AI Worker 使用独立 `backend/aiworker/.venv`（Python 3.11）。Windows/Linux 安装 PyTorch 2.7.1 + CUDA 12.6 与 Chinese-CLIP 1.6.0；macOS 使用 PyTorch CPU 版。RapidOCR 3.10.0 + ONNX Runtime 1.20.2 处理文字，OpenCV 4.12.0 + YuNet/SFace ONNX 权重处理人脸。Windows/Linux 使用 ONNX Runtime GPU 版，macOS 使用 CPU 版。Go 通过 stdin/stdout JSON Lines 调用并将 stderr 接入服务日志，Worker 常驻并复用 OCR/人脸模型。每个模块独立报告依赖与权重状态；缺失时任务中心不会把它显示为可运行。所有权重只从 `cacheDir/derived/ai/models/` 读取，模型下载脚本固定来源 revision 并校验 SHA256，不在服务启动时联网下载。新建的 embedding、OCR 和 face 任务默认强制使用 GPU；任务保存创建时的 `cpu` / `gpu` 选择，关闭 GPU 偏好后新任务使用 CPU。强制 GPU 不回退到 CPU，硬件不可用与推理失败分别进入任务错误码。Chinese-CLIP 遇到 CUDA OOM 时减半批量，单张仍 OOM 则将该图片记录为失败；语义搜索请求仍使用 Worker 的自动设备模式。搜索与建库推理共享同一串行 Worker。

向量以 512 维 Float16 保存在 `derived/ai/vectors/shards/`，每片有 JSONL 元数据与 SHA256，manifest 原子发布并标记已压实分片；元数据只含资源 ID、文件指纹、模型版本和片内位置，不保存文件路径。应用启动时将 Float16 shard 装入内存，完整校验哈希后才用于检索；模型/索引版本不兼容时重建派生索引。索引增量追加，累计 128 个未压实 shard 后由独立后台压实，每片最多 512 条；达到压实门槛后不因已有分片数量重复排队。检索将查询向量归一化一次，用半精度解码查表和有界 Top-K 堆代替逐条解码后的全量排序。Windows RTX 3060、本地 Go 基准 100,000 向量、512 维、31 次测量：p50 从 193.2 ms 降至 73.3 ms，p95 从 222.3 ms 降至 79.8 ms，每次搜索分配从约 2.4 MB 降至约 2.5 KB；索引堆约 129.8 MB。复现命令：`go test ./internal/services -run '^$' -bench '^BenchmarkVectorIndexSearch100K$' -benchtime=31x -benchmem`。

OCR 额外维护 `derived/ai/ocr-search-index.json` 倒排索引，索引项仅存 OCR 词元、模块版本和文件指纹，启动时从已提交的 OCR 批次核对并修复，任务批次提交后增量更新。查询会归一化全半角、CJK 空格/断行与中文标点，并在长中文短语上允许一个受限的常见混淆字或插入/遗漏；最终仍与当前 OCR 原文核验，精确结果排在近似结果之前。中文 OCR 回归集 8 个正例和近似负例，改动前精确率/召回率为 0/0，改动后均为 1.0（8/8 正例、0 假阳性）；该数字只代表固定合成文本夹具。向量查询支持 OCR 优先级，API 的 `matchReasons` 说明语义、以图、文字精确或近似命中。

人物服务从现有人脸批次生成中心向量候选分组；不再设置人脸总数上限，2,000,000 次中心比较上限仍用于限制运行时间，达到上限后剩余人脸保留为独立候选组。人物列表在内存中按当前照片目录汇总唯一照片数，只返回照片数最高的 50 组；用有界 Top-K 选择避免对全部分组排序，列表读取不逐张访问媒体文件。照片数相同时按封面资源 ID 与人物 ID 稳定排序；详情合并选择器以受限搜索获取目标，不向浏览器发送全量分组。详情媒体接口只聚合目标组，并把路径与文件指纹校验限制在当前分页。人脸分析仍需覆盖全库，才能准确计算最多照片的候选组。配置的 FFmpeg 可用时，HEIC/HEIF 人脸分析先转为最长边 4096 的临时 JPEG；worker 分析临时图，源文件路径与指纹仍按原图复核，批次结束后清理临时目录。全量重建按资源 ID 与脸序号排序；增量按序追加以避免重复重建，遇到较早资源或替换结果时确定性重建，并用新旧组的脸重叠迁移命名、隐藏和手动分配。若重建会合并多个已有人工修正的组，或拆分一个已有人工修正的组，则保留原分组映射，直到用户显式合并或拆分。聚类缓存每组归一化中心，避免每次比较临时重算。阈值 0.363 沿用 OpenCV SFace 默认参考值；项目没有可用于校准的本机已标注真人样本，因此没有基于合成向量调整阈值或声称降低误合并。名称、隐藏状态与纠错映射写入 `state/people.json`；`derived/ai/people-index.json` 只保存资源 ID、指纹、脸部框与分组引用，不复制特征向量。语义结果采用当前有效资源的精确余弦排序，纯 OCR/结构化结果按资源 ID 稳定排序；年份筛选使用当前 EXIF 拍摄年份，GPS 筛选复用既有 geohash 精度 5 地点 ID，人物、收藏与精选条件叠加在同一候选集合上，媒体库快照与文件指纹在返回前再次校验。当前不引入 HNSW、数据库或外部推理服务。

任务快照分两类字段：事实与派生。`results`（按解析状态分类的计数）与 `fields`（按字段统计的产出）是事实，随每个 32 张的批次原子提交并落盘；重启时按批次文件重放，与失败计数走同一条恢复路径。`planned`、`completed`、`estimatedRemainingMs` 与速度是派生值，每次快照按落盘的计数重算，不写入状态文件 —— 写进去就等于把某一刻的估计当成事实。已注册的分析模块清单由后端给出，客户端不维护第二份模块名表。

任务中心的界面拆成四段：运行（当前任务的进度、读数与控制，空闲时是开始分析的入口）、任务记录（历史任务与失败项）、每日计划（开关、时间与模块清单）、本机存储（派生缓存占用、AI 模型权重与各模块产物、相对路径与本机绝对路径）。等待队列作为「运行」段的附属面板贴在它下面，始终显示并明确呈现空队列状态。四段保持单列：并排两列时侧栏的分区目录无法判断用户正在读哪一列，宽屏的宽度改用在卡片内部（运行面板左右分栏、每日计划模块与人物开关左右分栏、本机存储两卡并排）。任务数据层收在 `hooks/useTaskCenter.ts`，存储数据层收在 `hooks/useStorage.ts`，面板在 `components/tasks/`；路由组件只排版。分析模块用芯片列出（`components/tasks/ModuleChips.tsx`），互斥选项用分段控件（`components/common/Segmented.tsx`），两类控件在各页共用同一套语义与键盘行为。单项启动和“按序启动全部任务”都复用 `AIJobService` 的持久队列；全部任务固定按 metadata、embedding、OCR、人脸顺序入队，缺少依赖或模型的模块跳过，前端在每项终结后刷新活动任务以跟上下一项，等待中的任务按执行顺序排列显示。失败项按「错误码 + 原因」在前端分组，同一原因的几百条路径折叠起来只留计数，展开才列路径。进度分母是本次任务实际要处理的张数（`planned`），不是整库规模：增量任务里整库大部分文件已经是最新的，拿整库当分母会让进度一上来就接近满格。

空闲时先给数字再给按钮：运行段在头部条与主体之间放一条「本次规模」（`components/tasks/TaskEstimatePanel.tsx`），把增量与全量两种口径的张数与预计耗时并排列出，当前模式那一行高亮。四个模块 × 两种口径由一次核算带来，切模式与切模块都不重新请求。模块与模式的选择态放在 `hooks/useTaskCenter.ts` 而不是组件里 —— 规模表、按钮上的张数说明与真正发出去的启动请求必须读到同一个 mode，分开存必然漂移。任务进入终态、用户清空历史、媒体库重新扫描之后都要让核算失效重算。每日计划按增量口径给出「预计下次运行」的张数与耗时。

本机存储信息集中在任务中心的「本机存储」段：媒体派生缓存的占用与清理读取既有的 `GET /api/cache/stats`，AI 模型权重与各模块产物的占用读取 `GET /api/storage/usage`。设置页只保留外观与阅读偏好、服务端配置、状态备份和关于；短分区在宽屏排两列（`xl:columns-2`），服务端那七组面板自带标题条并排两列，一组一块，不再是白卡里的白卡。

导航只有一条竖轴：应用级在左侧栏（`components/layout/Sidebar.tsx`），侧栏分「浏览」与「本机」两组，页面级分区挂在「本机」组里自己的入口下 —— 进入任务中心或设置，它自己的分区就展开在入口下面。分区清单只有一份（`utils/pageSections.ts`），侧栏与页面标题都从它出。当前分区由 `hooks/useSectionSpy.ts` 判定后写进 `store/sectionNavStore.ts`，侧栏据此高亮；两列并排时两个标题同高，只看位置认不出用户点了哪一列，所以点分区跳转时锁定到用户自己滚动为止。分区跳转由滚动容器自己滚（`scrollToSection`），不用 `scrollIntoView`：后者按视口定位，落点会压到顶栏上。侧栏在窄屏是抽屉，页面级分区也收在抽屉里；侧栏自身可滚动，窗口不够高时不会把底部入口挤出侧栏。

**按钮上的描边由全局规则决定。** `styles/global.css` 里按钮只清宽度（`border-width: 0`）不动 `border-style`：Tailwind 的 `border` / `border-b-2` 只改宽度，样式一旦被重置成 none，按钮上的描边会整条消失。区域层次因此靠「白卡 + 浅色标题条 + 发丝线」建立，不依赖按钮描边。

存储信息分两层给。`GET /api/storage/usage` 经过普通访问门禁即可访问，路径一律相对缓存根目录（`derived/metadata/ocr`、`state/ai_jobs.json`），局域网客户端也能看；`GET /api/storage/paths` 仅限回环访问，给出缓存根目录、工作目录、配置文件、Python 环境与各权重文件的绝对路径。完整路径不进入浏览器持久 store，也不向局域网客户端开放。任务记录展开时按需读 `GET /api/ai/jobs/:jobId/output`，给出这次任务自己的批次目录与占用；折叠状态不发起请求。

EXIF 解析器保存拍摄墙上时间、朝向、相机信息和 GPS 附属字段。缺少 EXIF/不支持格式属于正常解析状态，损坏文件计入单项失败。EXIF 日期只作为元数据返回；相册业务日期仍维持 `filename > folder > modified`，不会被 EXIF 改写。

## EXIF/GPS 与离线地点地图

地点页同时使用两套本地数据：旧的 Geohash 精度 5 分组为语义筛选和地点照片分页提供稳定 ID；地图接口则读取嵌入的省、市、区县边界，将有效 GPS 匹配到省份及最细可用的下级区域（无更细边界命中时退回城市），分别统计照片数。每次匹配都从当前 catalog revision 重新筛选元数据，要求资源仍是图片、路径通过 `PathValidator`，且大小与修改时间戳仍匹配；地图响应只含行政边界和聚合数量，不返回原始照片坐标或文件路径。唯一的例外是点云端点 `GET /api/locations/china/points`：它给的是照片位置的**粗网格聚合**，见下面的「点位与网格」。EXIF GPS 默认按 WGS84 处理并转为边界使用的 GCJ-02；显式标记为 GCJ-02 的坐标不重复转换，未知 datum 不参与地图匹配。

离线边界文件 `backend/internal/services/geodata/china-admin.geojson.gz` 由 AreaCity-JsSpider-StatsGov `2025.251231.260403` 版的 `ok_geo.csv.7z` 转换而来，数据更新于 2026 年 4 月 3 日。AreaCity 说明该版整合国家地名信息库 2025-12-31、腾讯地图行政区划 2025-11-19，并以高德行政区划和边界为主要来源；边界坐标系为 GCJ-02。上游将省市区三级边界包列为免费开源，乡镇边界是另一个付费数据包，本项目不使用它。上游仓库没有为该边界文件单独列出数据许可证；保留来源与版本记录，商业使用或再分发前应向上游及来源方核实授权。地图渲染与坐标匹配不发起外部地图、反向地理编码或 AI 请求。

数据更新时从 [AreaCity 发布页](https://github.com/xiangyuecn/AreaCity-JsSpider-StatsGov/releases/tag/2025.251231.260403) 下载 `ok_geo.csv.7z`，解压后运行 `python scripts/update_china_boundaries.py <ok_geo.csv路径>`。转换器仅使用 Python 标准库；它还原六位区划码、移除与父级同名同形的占位边界，并将其下级改挂到真实父级。当前下载包 SHA-256 为 `675C3E9B8DEC6444994D3EF53259A145304F6A957DB8A5E601E55C0B9E61E21A`。当前内嵌文件包含 3,214 个要素：34 个省、335 个城市、2,845 个区县。上游 3,209 条区县记录与 392 条城市记录中，台湾的 378 条区域边界为空而未嵌入；43 条重复层级被折叠。生成文件约 53.4 MiB，解压后的 GeoJSON 约 173.1 MiB，SHA-256 为 `05C2693D8FFBA8B6161E65470A7874AF17DBDD2EC86878F16C86721160FA0E93`。乡镇边界不包含在这套数据中。绘图用的轮廓文件由 `python scripts/simplify_china_outline.py` 从这个文件生成，不必重新下载上游数据。

上游本次发布说明指出，新疆和田新设的和康县、和安县尚无高德边界而未收录；它还更新了重庆两江新区相关区划。数据也不覆盖雄安新区等多数行政管理区。若以后接入乡镇边界，需要扩展当前只接受省、市、区县三级的转换器、后端层级匹配和地图下钻；本项目不包含上游单独标为付费的乡镇边界包。

**全国到区县逐级下钻。** 地点页按父子关系展示全国、省、市、区县；直辖市及同名省市重复边界会折叠，省直辖县级区域直接挂在省下面。各级照片数向父级汇总，因而城市计数包含它下辖区县的照片；当前区域自身有照片但没有任何下级边界命中时，`unmatchedAreaPhotoCount` 标出这部分数量。台湾的省级轮廓存在，但没有可用的城市和区县几何，因此按叶子处理。

**匹配与绘图用两份边界数据。** 点位判定要全精度：照片必须落在真实边界内，边界差几十米就可能归错区。绘图只要形状：全国图上省界偏移 0.01°（约 1.1 公里）看不出来，但下发全精度顶点是 18 MB 的 JSON。因此内嵌两份文件，来源同源、用途分开：

| 文件                                     | 用途     | 体积                       |
| ---------------------------------------- | -------- | -------------------------- |
| `geodata/china-admin.geojson.gz`         | 点位匹配 | 56.0 MiB（解压 181.5 MiB） |
| `geodata/china-admin-outline.geojson.gz` | 绘图     | 5.0 MiB                    |

轮廓文件由 `python scripts/simplify_china_outline.py` 从匹配文件生成（只用 Python 标准库，Douglas-Peucker 简化加按层级分档的容差：省 0.01°、市 0.004°、区县 0.002°；生成时关掉文件名与时间戳，同样的输入产出同样的字节）。它不改变匹配文件，只是把同一份数据简化成能画的样子。两份文件的区划码、层级与上级必须一一对应，由 `china_boundary_outline_test.go` 的交叉校验守住 —— 运行时不做这项校验，那会把 6 秒的匹配索引加载拖进绘图端点。

**几何按需下发，统计与几何分开。** 统计端点（`/api/locations/china`、`/api/locations/china/regions/:adcode`）只给数字，几何由 `GET /api/locations/china/geometry/:level` 单独下发，且只给当前视图需要的层级：全国给省，进入省给该省的市，进入市给该市的区县。整份轮廓不下发。改造前全国那一次请求是 18,013,977 字节的 JSON，改造后是 12,206 字节的统计加 265,877 字节（gzip）的省图。

**轮廓另有一条按区划码取的路。** 地图要画的是「去过的那些地方自己的形状」，而它们的父级在前端推不出来：直辖市的区县没有市一级（`310104` 直接挂在 `310000` 下），省直辖县级市在市级粒度里会卷到省，同一个粒度的地方列表里还混着不同层级的条目。因此 `GET /api/locations/china/geometry/features?adcodes=…` 直接按区划码查表（轮廓索引里本来就有 `byAdcode`），不必绕那层推导。实测体积：22 个市约 88 KB（gzip），48 个区县约 300–400 KB。

进程启动时在后台预热匹配索引：它有 797 万个坐标点，加载要 6 秒、常驻约 1.4 GB，放着不管的话第一个打开地点页的人要等这 6 秒。轮廓索引小两个数量级（77 万个点、解析 0.6 秒以内），整份常驻。匹配结果按 `(catalog revision, 分析记录版本)` 缓存，重复查询不再重跑整库点位判定；边界匹配用纬度分桶缩小每次点在多边形检查的边集合。分析记录的版本号由 `AIJobService.RecordsRevision()` 给出，记录增删改时递增，缓存因此不会给出过期计数。统计端点的 ETag 用匹配文件的内容指纹（sha256 前 8 字节）；绘图端点的 ETag 只用轮廓文件的指纹并带长期缓存 —— 几何不随媒体库变化，不必因为换了张照片就重下。

### 点位与网格

行政区匹配答得出「落在哪个市」，答不出「具体在哪儿」——后者要靠照片自己的坐标。匹配阶段本来就算出了 GCJ-02 的经纬度（点位判定要用），用完就丢；现在留住它，画在地图上。

**点位只以网格聚合下发。** 一格是一段约 1 公里到 50 公里的范围，格里的照片可能横跨一条街，也可能是一整个景区。响应里只有「这一格在哪儿、那儿有多少张照片」，没有资源 ID、没有路径、没有单张照片的经纬度。这是一次有意的口径放宽，边界写在这里：

> 服务端手上本来就有比 0.01° 更细的位置（它拿来做点位判定），但**对外给出的最细粒度是 0.01° 一格**。同一台服务器本来就通过媒体接口提供这些照片本身，网格化只是把「连续坐标」降成「格点计数」，不新增一类信息。

格边长只认六档（0.01 / 0.02 / 0.05 / 0.1 / 0.2 / 0.5 度）：它是「画多细」的档位，不是一个连续参数。白名单让前端能按画布大小挑档 —— 小地图只有 236 像素宽，几公里的一格在画面里不到一个像素，点会糊成一片噪点，因此足迹页固定用 0.2 度这一档。格数超过 4000 时服务端自动调粗，`cell` 里回报实际生效的那一档。

格心取 `floor(lon/cell) * cell + cell/2`，**不是照片坐标的平均值**：平均值会把点拉回真实位置，格心不会 —— 一格里到底有没有照片，地图上看不出来，也不该看出来。

时间过滤与其它端点不同：**没有可信拍摄时间的照片一律保留**。它们有真实位置，只是没法判断在不在区间里；一并丢掉的话，一张没设时钟的照片就会让整张地图空掉。它们在每格的 `untimed` 里单独计数。

### 时间维度：三种时间，只用一种

地点页的轨迹叙事只用 **EXIF 拍摄时间**（`dateTimeOriginal`）。库里有三种「时间」，各管各的，不混用：

| 口径           | 来源                             | 用途                                 |
| -------------- | -------------------------------- | ------------------------------------ |
| 文件夹名年份   | 目录名里的 `19xx/20xx`           | `/photo/years/:year` 年份墙          |
| 相册业务日期   | `filename > folder > modified`    | 相册在时间轴上的位置                 |
| EXIF 拍摄时间  | `dateTimeOriginal`               | **地点页的时间轴、轨迹与到访**       |

EXIF 的 `dateTimeOriginal` 通常不含时区，因此保留相机记录的墙上时间，按**拍摄地的当地日期**比较 —— 这正是「我在杭州待了几天」这种叙事的口径；接口不声称给出绝对时刻。

**可信性只看解析结果，不看文件时间。** 解析失败、年份早于 1990 或晚于当年加一的照片，时间标记为不可信：它们照常计入空间统计，但不进时间轴、轨迹与到访，界面如实给出这部分的数量（`untimedPhotoCount`）。不用文件 mtime 校验 —— 照片常是事后拷进库的，mtime 与拍摄时间能差出几个月，拿它当基准会误杀大量正常照片。

**时间索引在缓存里建一次，区间在读取时过滤。** 匹配阶段已经反序列化了 `ImageMetadata`，多解析一个 `dateTimeOriginal` 不带来额外 I/O。匹配结果里的照片按拍摄时间升序存放（时间不可信的排在末尾，仍按相册序），缓存键**不包含**请求的时间区间 —— 区间过滤发生在读取时，扫一遍缓存里的切片即可。这样不会出现「缓存里只有某一年的数据」这种错配，缓存也不会因为用户拖时间轴而反复重建。请求级的时间区间只进入 HTTP 的 `ETag`，换区间后旧响应不会命中 `304`。

**到访按日历日切分，阈值是量出来的。** 同一区域的照片按拍摄时间排序后，相邻两张的**日历日间隔 ≤ 2 天**算同一次到访，超过则另算一次；列表和照片墙共用同一个切分函数，两边不可能对不上。按日历日而不是按小时，是因为「晚上八点和第二天早上八点」这种跨夜行程在人看来是一次。2 天这个阈值来自本机库的实测：同地点相邻照片的日间隔在 1 天 328 次、2 天 132 次、3 天起断崖式下跌到长尾，≤ 2 天合并、> 2 天另算正落在拐点上。阈值写成常量 `chinaVisitMaxGapDays`，修改需同步界面说明。

**轨迹的停靠点是行政区，不是照片。** 停靠点 = 连续落在同一区域的一段照片，粒度跟当前地图下一级走（全国＝省级，省＝市或省直辖区县，城市＝区县）。照片匹配到最细的可用区域，再向父级汇总；城市地图的轨迹因此落到区县，省地图则落到市或省直辖区县。后端只返回停靠点的**区划码与名称**，折线由前端用区域几何的质心连出来 —— 这样响应里依然没有任何照片经纬度。相邻停靠之间间隔超过 2 天就不连线，否则相隔两次出行的照片会被画成一条横跨半张图的假路径。



## 媒体管线

### 图片、缩略图与预览

- 缩略图采用内存 LRU 与磁盘 JPEG，源版本、尺寸和编码版本参与缓存键。读锁覆盖生成与查询，重配和清理使用写锁。
- 渲染图按固定宽度阶梯分档（320 / 640 / 1280 / 1920 / 2560 / 4096，见 [rendition.go](../backend/internal/services/rendition.go)）：请求宽度向上对齐到档位，档位进缓存键与 ETag，换档就是换一份产物。渲染不裁剪，各档宽高比一致，前端才能用 `srcset` 让浏览器自选档位。
- 内容版本号形如 `<mtime_ns>-<size>-r<算法版本>`，由源文件 stat 得到。媒体列表 DTO 带出版本号，前端把它拼进渲染图 URL；服务端比对一致时回 `immutable`，浏览器长期缓存，重复打开页面不再为图片发请求。
- 派生 ETag 为 `"<版本号>-<档位宽度>"`，不再对响应字节做哈希：条件请求只需一次 stat 加一次字符串比较，判定提到生成之前，冷缓存上的 304 也不必解码。
- 坏文件要标出来，别让用户对着破图图标猜。判定分两处：尺寸服务读图片头失败当场标 `undecodable`（需要服务端转换的 HEIC/HEIF/TIFF 不算坏）；图片头能读、像素数据却是截断的，只有真正解码一次才暴露 —— 渲染路径解码失败时回调尺寸服务补记，标记跟着文件走，文件被替换后判定作废。尺寸缓存早于这个标记，磁盘上的旧记录按「宽高都是 0 就是读不出图片头」补判，不必让整份缓存作废重探。
- 并发同时受 `min(12, NumCPU)` 和 192 百万像素预算限制；大图先 Box 预缩放到目标约两倍，再 Lanczos，不能只按图片张数估计解码内存。
- 像素预算闸门是加权信号量，容量就是预算本身：一次申请超过容量的权重会永远阻塞，把整条渲染链路（连同 HTTP 请求）一起挂死。因此权重永远压在预算以内，超过预算的大图（拼接全景能到 277MP）改走 ffmpeg 按目标宽度缩放后再解码，内存有界；ffmpeg 不可用时才退回进程内解码。本机实测：一张 6184×44767 的全景把重建任务卡在最后一项，修复后同一张图 3.9 秒出图，峰值内存约 1.2GB。
- HEIC/HEIF/TIFF 通过可选 ffmpeg 转换，整图转换与缩略图缓存分开。工具缺失或失败返回不支持格式，前端提供占位与说明。
- 连续阅读使用按目标宽度缓存的 `/api/previews`，单张/双张使用原图；预览规则与响应字段在 API 维护。
- 前端所有渲染图走 `components/common/RenditionImage.tsx` 一个出口：按槽位宽度与像素比选档，给出 `srcset` 与 `sizes`。照片模式的大图预览不走 `srcset`，而是按舞台尺寸与图片原始比例算出实际显示宽再乘像素比与缩放倍数取档 —— 视口宽不是显示宽，照视口宽要图会命中 4096 档（服务端对更窄的源图原样返回原图），一张 3.7MB 的原图就为了看 788 像素宽的一屏被整个拉下来。舞台尺寸用 `ResizeObserver` 量，量到之后才发请求，避免先要一张再改 URL。
- 视频封面优先 ffmpeg（同文件合并、全局最多两个任务），按视频流时长定位、短视频取片头，无帧时从片头重试。等比缩小、不放大、不补边；没有服务端封面时浏览器通过 Range 抽帧并回传。
- `useVideoCover` 的一次 effect 拥有探测、抽帧、上传整条链，切换/重试/卸载均取消并忽略迟到结果。探测 20 秒、抽帧 30 秒期限包含挂起请求；完成释放媒体元素、canvas、网络监听和计时器。

### 缓存重建任务

`internal/services/cache_rebuild.go` 的 `CacheRebuildService` 在后台重建派生缓存：枚举库快照里的相册与媒体（只在本机内部用绝对路径），按所选范围（缩略图 / 预览图）生成对应档位，video 不参与（ffmpeg 抽帧与转码代价另算）。任务状态机与 SSE 订阅复刻扫描任务的做法：终态事件后关闭连接。运行期间每 500ms 推一次进度快照 —— 逐项推太密，不推进度条就十分钟不动，看着像卡死了。

前端 `components/tasks/CacheRebuildPanel.tsx` 发起任务（随派生缓存一起收在任务中心的本机存储段），`hooks/useCacheRebuild.ts` 订阅 SSE，`store/cacheRebuildStore.ts` 持有 jobId 与进度 —— 只持久化 jobId，进度每次连接重新获取。切走页面再回来，任务仍在跑，进度接得上。

### 视频元数据与转码

`VideoInfoService` 优先 ffprobe JSON，缺失或失败则解析 ffmpeg 输入头；工具检查与探测均有超时，超时不缓存部分输出。成功摘要按规范化路径、大小、纳秒修改时间缓存到最多 512 项内存 LRU，同指纹 singleflight，失败可重试。单条/批量接口共用 DTO 与当前路径校验，批量保持顺序和逐项错误。

视频发送按“按需转码 → MP4 faststart remux → 原文件”选择。MKV/AVI/3GP 等浏览器无法使用的容器、冷门编码按需转 H.264 + AAC；moov 在末尾的 MP4 可仅 remux。工具不可用时降级到后续管线。

- faststart/转码缓存只命中非空普通文件，拒绝自身链接、目录和空文件；选择后再次复核。生成写目标目录的独占临时文件，成功并复核后原子发布，失败只清理本次临时文件，不删除占位目录或无关条目。
- 转码任务键含源路径、大小、纳秒修改时间与 profile；同版本去重、全局限流。新请求看到新版本时取消旧任务，启动与发布前再比指纹；被替换任务仍登记待回收，退出等待新旧 worker。
- 状态查询与订阅共用当前版本状态，磁盘有效缓存优先于旧进度/失败。仅活动任务保留订阅，其他状态发送完整终态并关闭；进度、终态、通道关闭与取消由同一任务锁串行保护。
- 大小和修改时间均未变化的内容覆盖不在指纹检测范围内；一键全清可重置内存元数据代次，使旧探测无法回填新缓存。

### 发送与浏览器生命周期

原图与视频共用 `serveMediaFile`：每响应独立打开最终文件，以同次 `f.Stat` 得到类型、长度、mtime 与 ETag；完整或单段 Range 流式发送，完成、断连、HEAD、304 与发送前错误均释放句柄，不缓存整段媒体或旧文件句柄。外部原地写入不构成事务隔离。

缓存协商要求浏览器重新验证，源校验先于条件请求；弱比较、If-Range 强校验与错误码集中在 API。播放/抽帧另外使用随机 `playback` URL 标识隔离同页解码缓冲：同次播放与 Range 保持地址，切换、重试、转码完成生成新地址；标识不参与鉴权、服务端任务键或持久活动。

`state/backups/` 保存用户手动恢复前的备份，不属于派生缓存，不参与缓存清理。对外只给相对缓存根目录的路径；绝对路径由回环保护的本机接口单独提供。对外备份仅使用资源 ID；另存的内部封面映射仅供本机恢复旧状态，不对外下载。

派生缓存的写入攒批：媒体尺寸探测出的记录先在内存里排队，一页媒体处理完再一次性写盘并刷一次。逐条刷盘的话，一页两百张照片就是两百次 fsync —— 实测冷缓存下翻五页照片流要 1.8 秒，攒批后 0.55 秒。攒到一定量会自己落盘，调用方忘了刷也不会把内存吃满。

启动只读写当前分层布局，不读取、移动或删除旧顶层状态。偏好部分更新在同一写锁内读改写并原子落盘，避免并发修改主题时覆盖收藏/历史；高频活动独立文件，批量活动校验后一次写入。归一化后业务字段相同的活动保留原时间与版本，整批无变化时跳过复制、排序和落盘；有效变更仍先原子写盘再发布内存。

状态备份由 `StateBackupService` 组装偏好、活动与封面快照。预览提供状态摘要，导入时在各 store 锁内比较并原子提交；偏好相关类别在同一文件内合并，跨文件逐类报告结果，不宣称全局事务。封面存储先落盘再发布内存，写盘失败不污染当前视图。设置页备份面板只在组件内存中保存所选文件与预览，离开即释放；写入确认后刷新失败仍保留完成报告。

后台维护在启动及每小时运行，以 `os.Root` 限制删除在五类派生目录内，仅处理哈希命名的完整普通文件，不跟随链接、不进入 `state/` 或处理临时文件。按年龄与容量从旧到新清理，十分钟内的新文件保留，因此容量为软上限；`cacheMaxSizeMB: 0` 只关闭容量淘汰。

SIGINT/SIGTERM 触发停止接收连接、取消扫描/转码并强制刷新扫描缓存；HTTP 等待最多 5 秒，后台清理使用 10 秒退出窗口，维护任务也取消并等待结束。

## 前端状态与异步写入

### 临时选择与批量操作

`selectionStore` 仅保存至多 1,000 个待操作 ID 与少量选择摘要，不持久化。App 按路由与搜索/视图/年份/最少图数维护作用域；改变作用域清空选择，排序和追加分页保留。列表网格的选择模式使用独立复选卡片，避免星标、导航和选择动作竞争；“选择已加载项”不隐含全库选择。提交期间固定清单并禁止重复操作，跨页面的迟到确认仍更新查询缓存，但不清空新的作用域。收藏与已读写入使用已有 Query 状态，不增加长期媒体数据副本。

照片侧另有一份临时选择（`photoSelectionStore`）：照片墙与精选页勾的是「这一张」，
条目形状与相册选择不同（要带文件名与所属相册才能做并排对比），混在一份选择里
两边都别扭。它同样不持久化，作用域是相册 ID 或精选页。

精选本身只有客户端一份真相：`usePicks` 缓存精选的文件 ID 集合，它跨相册、跨页面
共享，因此在任意一处加入精选，照片墙、精选页与大图预览里的同一张照片会同时更新 ——
不必去改各个列表自己的缓存。写入先改本地集合（界面立刻响应），服务端确认后再取
一次权威结果；写失败退回原样，界面不停在服务端并不认可的状态上。服务端在媒体项上
另带 `picked` 标记，集合尚未回来时用它先把状态画出来。

### 工作台模式

工作台模式（`appMode`）就是目录的内容属性（`contentKind`）：`photo` / `comic` 两档互斥，没有不过滤的第三档。属性写在配置里（`mediaRoots[].kind`），目录下的相册与集合在发布时一并继承，没有单本相册的归类动作。服务端记住上次用的是哪一侧（`Prefs.appMode`，`state/web_settings.json`），它只是**落地页偏好**；当前在看哪一侧由 URL 路径前缀决定。

- 模式决定列表呈现哪一半，也决定相册点开进照片墙还是阅读器：照片工作台只列照片目录的相册，漫画工作台只列漫画目录的相册，两套菜单与措辞各自成套。
- 服务端列表接口的 `kind` 查询参数（`photo` / `comic`）必填，缺失或非法返回 `400 invalid_kind`：子节点、未读、随机、标签、标签相册与搜索按目录属性过滤。集合继承所属目录的属性，因此同样参与过滤——漫画目录下的集合不会出现在照片工作台里。它的 `albumCount` 恒为全部后代，但集合的所有成员都在同一媒体根（同属性），所以这个计数天然按侧，无需再拆一份。manifest 的 `albumCount` 是全库总数，另给 `photoAlbumCount` / `comicAlbumCount`，集合同理有 `photoCollectionCount` / `comicCollectionCount`。
- 过滤发生在分页之前：发布时预切好的有序切片按属性筛成子序列，游标里的偏移是过滤后列表的偏移。属性进游标作用域，跨属性复用被拒绝为 `invalid_cursor`。
- 未读/在读派生按 `(catalogRevision, activityRevision)` 缓存，缓存与属性无关，属性过滤是请求期后置筛选。未读下标只收漫画相册：照片目录下的相册不记录阅读进度，没有「未读」这个概念。
- 前端查询键带模式段（`["library", ..., "mode", mode]`），切模式即换键自动重取，旧模式缓存保留。媒体清单与 `nodes/query` 与模式无关，键不带模式。收藏与历史的资源 ID 集合不分类型，由前端按摘要里的 `contentKind` 客户端过滤；`hooks/useFavoritesByMode.ts` 把「当前侧可见的卡片 / 本侧计数 / 真失效的条目」收在一处，收藏页与首页共用它，口径不再分叉。
- 收藏里的智能标签按名解析（`POST /api/tags/query`），接口同时给出两侧的册数：客户端据此区分「这个标签在库里不存在」（失效，可清理）与「它只属于另一侧」（不可见，但不是失效）。把两者混为一谈会导致用户在另一侧点一次「清理失效收藏」就删掉自己的收藏。
- 阅读器整屏脱离 AppShell，侧栏不可见，顶部提供工作台 chip 切模式（切模式即离开阅读器回到外壳）。
- 模式也决定视觉基调：`<html data-mode>` 由 `WorkbenchModeProvider` 写入，CSS token 按 `:root[data-theme][data-mode]` 组合覆盖（`--brand*` / `--feature-bg` / `--mode-tint`），画布与文字保持中性灰阶。封面画幅同样按侧取默认值（照片 1:1、漫画 2:3），见 `utils/workbench.ts` 的 `coverRatioForMode`。
- 首页首屏按侧各成一套：漫画是「继续阅读 / 未读」两块面板，照片是「随手看看」的跨相册照片墙加「接着看」一块面板。照片墙的数据源是 `GET /api/library/media-feed?kind=photo&scope=random`（随机几本相册的照片，服务端交错排列），组件在 `components/home/PhotoFeedHero.tsx` 与 `components/wall/PhotoStrip.tsx`（只铺给定张数、不滚动的静态照片条），翻页由 `hooks/useMediaFeed.ts` 负责。
- 照片侧的「接着看」与漫画侧的「继续阅读」对称，数据源不同：漫画读的是阅读进度，照片读的是访问历史。`hooks/useHistory.ts` 的 `useHistoryCards` 把 `GET /api/history` 与 `POST /api/library/nodes/query` 合成按侧收敛的卡片列表，组件 `components/home/ResumeHero.tsx`（首页首屏专区）、侧栏的「继续」区与「最近浏览」页共用它。它额外返回 `resolvedCount`（仍存在于媒体库里的访问记录条数），用来区分「这一侧没有记录」与「访问过的相册全被移出媒体库」——两者的提示语不同，后者才提「相册可能已移动」。
- 措辞与计数单位的唯一真相源是 `utils/workbench.ts` 的词表（`workbenchCopy(mode)`），两侧共用组件从**卡片自身的** `contentKind` 取词，而不是从当前工作台取：一张卡永远知道自己属于照片还是漫画，取不到时按照片兜底。照片说「张 / 本 / 浏览」，漫画说「页 / 卷 / 阅读」。
- 「那年今日」的下标表在发布期建好：把各相册从文件名推断出的拍摄日期按月-日归桶（`library_page.go` 的 `onThisDay`），请求期只按属性与年份过滤。它靠拍摄时间成立，因此只在照片侧有意义 —— 漫画侧不出现这一段。
- 索引维度按侧分：照片按年份（`components/home/YearTimeline.tsx`），漫画按作品（`components/home/SeriesTimeline.tsx`，集合即作品）。两者共用 `components/home/Timeline.tsx` 的视觉骨架。照片侧年份卡的主操作是打开年份照片墙（`routes/YearPhotos.tsx`，`/photo/years/<年份>`）：`GET /api/library/media-feed?kind=photo&scope=year&year=<年份>` 按年份归组取出各相册的照片，每张带 `albumId` / `albumName`，大图预览的标题可点回原相册。

### 查询、导航与网格

- TanStack Query 管理库、媒体、偏好、收藏与历史；Zustand 管理本机 UI、阅读器和扫描连接会话。主题与 Toast 在应用层统一挂载，阅读器独立于 AppShell 但仍有错误边界与访问门禁。
- 路由在 `App.tsx` 懒加载，**模式进 URL 路径**：`/photo`（照片库）、`/photo/recents`、`/photo/favorites`、`/photo/picks`（精选照片）、`/photo/albums/*`、`/photo/tags/*`、`/photo/travels`（足迹）、`/photo/people`（人物候选）；`/comic`（漫画库）、`/comic/unread`、`/comic/recents`、`/comic/favorites`、`/comic/albums/*`、`/comic/tags/*`；漫画阅读器 `/comic/read/:albumId` 使用相册 ID 和 0-based index，视频加 `type=video`；设置页 `/settings` 与模式无关。根路径 `/` 按服务端记住的偏好落到某一侧。标签按单个路径段编码，路径段只解码一次（从原始 pathname 切段，不用 `useParams`），直接打开链接的返回有应用内兜底。
- 足迹页在 `/photo/travels`，地点详情在 `/photo/travels/place/<六位区划码>`。筛选状态（时间区间 `from`/`to`、归并粒度 `level`）放查询参数，时间区间是跨层级的一维：换粒度与下钻都带着它，缺省表示全部时间。旧的 `/photo/locations` 与坐标聚类相册 ID 一并作废，不留兼容跳转。
- 足迹页的组成：`routes/Travels.tsx` 是通栏单栏的骨架（页头 + 数字台 + 时间轴 + 行程目录），`components/travels/TravelMiniMap.tsx` 是嵌在数字台右端的只读小地图（离线行政边界 + 照片位置的点云，236×104），`components/travels/TravelTimeline.tsx` 是按真实时间比例铺开的时间轴（逐月的张数画成一条平滑曲线，行程是线上的珠子，两端各一个可拖动的抓手），`components/travels/TravelTrips.tsx` 是行程目录（按年分组，一行一段，点开才就地展开照片），`components/travels/TravelPlaceList.tsx` 是从小地图下缘展开的「去过的地方」清单。段的照片按需取回：`hooks/useChinaLocations.ts` 的 `useChinaTripMedia` 在展开或点开时才发请求。
- **行程不随时间区间重切。** 段是按「粒度 + 两周间隔」切出来的，`/trips/:index/media` 按段的下标寻址 —— 段若随区间重排，下标就再也指不到同一段照片了。因此足迹页的行程列表与行程照片端点**都不带时间区间**，时间带上的刷选只决定哪些段被点亮、地图与数字台过滤到什么范围。查询键里因此有「全量」与「区间」两套（`useChinaTripsAll` / `useChinaSummaryAll` / `useChinaPlacesAll`），两者不能共用同一个键，否则会互相顶掉。
- **模式有且只有一个真相源：URL 路径前缀。** 服务端 `Prefs.appMode` 只决定根路径落到哪一侧；前端 `appModeStore` 只镜像这个偏好，不持有「当前模式」。`WorkbenchModeProvider`（`components/layout/`）挂在应用最外层，从 `useLocation` 推导模式并经上下文下发，因此整屏脱离外壳的阅读器也在同一套上下文里。切换模式 = 导航到对侧对应页 + 写回偏好，两件事缺一不可。
- 模式切换的语义只有一张表（`utils/path.ts` 的 `counterpartRoute`）：两侧都有的同名页（最近 / 收藏 / 标签）一一对应；相册与阅读器只属于一侧，未读只属于漫画侧，精选只属于照片侧，它们都回落到对侧首页。
- 相册入口按内容属性分派：照片目录的相册 `/photo/albums/<相册 id>` 直接渲染照片墙，漫画目录的相册重定向到阅读器。属性由服务端给出（所属目录的 `kind`），前端不按图片数量推断。
- 常驻导航仅取 activity-summary、随机相册或已加载 dashboard；首页一次取得未读计数、有限预览与在读摘要，不下载全库。完整未读索引按“库 revision + 活动版本”复用，列表按需分页。
- `AlbumGrid` 绑定最近的纵向滚动祖先，网格/列表只挂视口附近条目。
- 照片墙（`components/wall`）按每张图的真实宽高比做自适应排布：宽高比来自服务端媒体分页返回的像素宽高（由 `MediaDimensionService` 读图片头得到并缓存），排布算法是纯函数，容器宽度或密度变化时重算。行高度由算法确定，`Virtuoso` 只负责按行虚拟化；虚拟窗口参数保持在安全范围内，避免尺寸树展开过深触发爆栈。总数占位保留整本相册的滚动长度，行范围换算回媒体序号后由 `useMediaGridPagination` 连续补页，失败保留内容并暂停自动请求，显式重试恢复。容器与窗口的验证要求见设计文档。
- **大图预览跨页连续浏览**（`components/wall/PhotoViewer.tsx`）：预览翻到的位置是「已加载序列」里的下标，序列本身分页到达。翻到已加载末尾时预览自己去取下一页（`hasNextPage` / `onLoadMore`），取到后自动接上下一张，不必回墙上继续；离末尾还有三张时预加载下一页。连按「下一张」时位置记在 ref 里而不是 props 上（props 一次按键只更新一次，连按会被吞掉一半），没加载出来的次数先记着，页到了一次补上。取页失败保留已加载内容并给出手柄（底栏「重试」），再按一次「下一张」也会重试。页数读数报的是服务端总数，不报已加载条数。关掉预览时照片墙按 `scrollToIndex` 回到刚才看的那张。

- 扫描连接状态与任务状态分开，原生 EventSource 错误不直接等同扫描失败；断线保留进度并阻止重复启动，重连仅 GET 同一任务。“停止跟踪”只释放客户端连接。共享订阅不随路由卸载，迟到/畸形消息不污染新任务。

### 活动、收藏与历史

- 精选（`state/picks.json`）与收藏是两份数据、两种语义：收藏标记「这一本值得留着」，
  精选标记「这一张值得留着」。两者各写各的文件，互不覆盖也不会互相清理 ——
  「清理失效收藏」不会动精选。精选只属于照片侧：照片墙与精选页都是照片侧的界面，
  漫画那边有阅读进度与已读状态。精选条目是媒体文件 ID（`f_`），上限 5000 条。
  内存里同时留有序列表与集合：列表给展示顺序（最近加入在前），集合给 O(1) 的
  「这张在不在精选里」——照片墙每一格都要问一次。写入是整份文件原子替换，
  与收藏同一套做法；5000 条的量级下单次落盘在毫秒级，不需要另设增量日志。
- 精选与目录数据分属两处：目录快照里不存精选，请求期按当前精选集合给媒体项打
  `picked` 标记。精选页要跨相册列出这些照片，因此目录侧另建一张「文件 ID → 所属相册
  与序号」的反查表（存下标不存副本，避免为大库再留一份媒体摘要）；同一份文件同时
  出现在真实相册与「本目录媒体」虚拟相册时优先用真实相册，判定不依赖 map 遍历顺序。
- 精选页的分页游标作用域里带精选自身的版本号：精选一变，旧游标立即失效，
  新加入的照片不会把已经翻过的页顶走一格。
- 漫画按 `albumId + image` 保存页码；视频按 `albumId + video + itemId` 保存毫秒位置。图片最后一页、视频 98% 派生完成；无图片活动表示未读，纯视频相册改用视频活动。照片浏览不留进度记录，因此没有 `photo` 活动类型。
- 未读判定只针对漫画相册（看 `image` 活动）；照片目录下的相册不记录进度，也就不存在未读。
- 阅读进度恢复成功前禁止写入，只有明确的 `activity_not_found` 可当新记录；其他失败持续提示并可重试，避免自动播放/初始页覆盖旧位置。保存失败重试使用当前有效位置，切资源忽略旧失败，卸载 keepalive 仅尽力写入。
- `useImageProgressSync` 收拢图片进度的 600ms 去抖、保存反馈与确认后的缓存刷新。浏览分页的卡片进度只补充已加载漫画的活动，保留在读与已完成状态。`activityApi` 持有会话级图片写入队列：串行发送，尚未发送的同相册进度合并为最新值；相同在途请求可共享确认。显式已读、重置、批量操作和活动备份恢复形成边界，不跨边界合并。失败拒绝相关等待者后继续后续任务，不自动重放写入。
- 图片卸载补写经过同一队列，已发送的小请求带 `keepalive`；浏览器关闭后尚未发送的任务只能尽力补写，收到成功响应才代表已落盘。队列只协调当前浏览器会话，不提供多标签页的全局顺序。
- `useVideoActivity` 收拢视频恢复、节流保存与卸载补写，回调通过 ref 转发以避免查询重启；视频播放状态保持独立。活动写入由应用级 `useLibraryActivitySync` 统一失效首页、计数与未读缓存。
- 收藏/历史/偏好写入成功后先将服务端确认结果写共享查询缓存，再后台刷新，后续 GET 失败不能复活已删除记录或回退新设置。切换收藏读取当前缓存，首次查询未确认不盲写；清理失效项只过滤已知缓存，不凭移除清单构造空列表。
- 首页、集合与标签相册使用 `useLibraryList` 无限分页，服务端 `library_query.go` 统一筛选与排序。每个不可变库快照拥有最多 16 个查询结果的 LRU，翻页复用结果；游标同时绑定查询与历史排序快照。年份/作品索引和统计独立于已加载页数。请求取消、后续页重试和游标失效后的整链重取由 hook 处理。阅读器上下文携带查询及后续游标，在已加载边界补页，卸载/换卷取消请求；失败提示返回列表刷新，不混用旧顺序。
- 列表排序共用一套口径：「按拍摄时间」（照片侧）/「按加入时间」（漫画侧）用业务日期（拍摄时间 > 文件夹名日期 > 修改时间），与后端 `albumMoreRecent` 相同；缺业务日期时退回修改时间。首页、集合、标签由服务端执行；收藏与最近等有界列表继续使用 `utils/cardSorting.ts`。首页的「库内一览」默认不再重复摆年份归组的那些集合（`library_query.go` 的 `excludeYearTargets`），搜索或按年份筛选时仍给出全部命中。
- 最近与收藏分别处理查询失败、资源失效和筛选无结果，保留已加载卡片。“最近看”只在需要排序时读历史，按 `openedAt` 降序，同时间或未访问按名称；历史确认结果同时同步 `history` 与已存在的 `prefs.history`。
- 访问记录使用真实相册名称和图片总数，只依赖相册身份，不随媒体分页重复记录；视频数量不替代图片总数。可点击星标与链接分离，星标使用共享 mutation，不为每张卡订阅完整收藏列表。

### 服务端配置表单

`useServerConfigSave` 在同一 QueryClient 内通过共享 mutation scope 串行写入，覆盖卸载重进；LAN 凭据变更后的会话建立也属于该串行流程。保存开始/确认取消旧 GET，读取传递 AbortSignal 并禁用 HTTP 缓存，防止迟到读取回退新值。

- 显示优先级为草稿 → 最新保存中值 → 失败输入 → 确认值，状态与当前可见值对应。失败输入仅在会话内缓存，保留 false/0/空数组，不持久化路径或令牌，凭据不进入失败缓存。
- 输入法组合期间，媒体根整组或当前文本/数字字段暂停自动保存；确认后重新计时并核对草稿版本。失焦确认组合输入，删除字段/卸载清理未提交计时，已发出的请求按序完成。Enter/Esc 语义见快捷键文档。
- 重试仅提交未被新草稿或排队写入覆盖的失败值；显式重新读取在无排队写入时执行，暂禁表单，失败/取消/卸载保留输入，忽略迟到结果。
- 根目录写入遇到网络/超时/5xx 时标记结果待确认，不能推断服务端没写入。重试或读取确认后清客户端旧库并提示扫描；结果未确认、新根草稿或保存中禁用扫描。Esc 只撤销本地输入。
- 目录选择只在本机管理接口浏览，后端返回路径与平台根，前端不探测 OS/拼路径；弹窗持有临时路径、取消旧请求并忽略迟到结果，确认才进入配置保存流程。后端每批读取 256 项、使用固定大小堆生成最多 200 项有序页，不缓存完整目录。

属性、菜单、帮助、复制与系统打开复用现有组件/hooks。属性按节点/图片类型请求，聚合标签不冒充目录；复制优先剪贴板 API、失败用所属 dialog 内临时选区并恢复焦点；系统打开权限用 `useFsCapabilities` 共享查询，未知时关闭，设置确认后取消旧查询并发布权限。键盘细节只在快捷键文档、视觉细节只在设计文档维护。

## 验证与性能对照

### 媒体处理历史对照

以下为历史本机性能对照，仅供显式性能优化任务复测，不是通用容量承诺；原始实验过程可查 Git 历史。

- 缩略图（2026-11-01，Windows amd64、Go 1.24.3、16 核）：24 张合成 2048×2048 JPEG，8 请求 worker，目标 320×350；旧实现固定四路并发 + 直接 Lanczos，当前为像素预算 + Box 预缩放。堆每 2ms 采样，吞吐收益伴随更高内存使用。
- 视频元数据（同日 Windows、i7-10700K）：只读本地 10.51 MiB、720×1280、25.899 秒样本，预热后 32 次查询、三次取中位数；基线为每次外部探测。Go 分配不含工具子进程，保持大小/mtime 的覆盖需手动清缓存。
