# 设计目标、验证与待办

本文定义设计决策空间、质量要求与已知风险。现有 [tokens.css](../frontend/src/styles/tokens.css)、[global.css](../frontend/src/styles/global.css)、组件、截图及布局测试描述当前实现，均可随新的设计方案演进。快捷键契约见 [SHORTCUTS.md](./SHORTCUTS.md)。

## 设计决策权限

用户提出界面优化或重设计时，AI 应根据目标和实际内容形成完整方案，自行调整相关布局、组件和视觉系统。旧文档、旧注释与旧截图中的具体样式不构成继续沿用的要求。

- 可重新安排首页内容、导航、搜索、侧栏、阅读控制与设置页，允许拆分、合并或替换现有展示组件；改动范围由用户目标决定，不必局限为局部样式补丁。
- 可调整容器宽度、列数、断点、封面比例、字号阶、主题配色、材质、圆角、阴影与动效。现有 1600px 容器、1.6 倍封面比例、双栏舞台、固定列数和底部工具条都是可替换的方案。
- “内容优先”“克制”等表述用于判断效果，不限制品牌表达、色彩或排版探索。不预设只有冷灰、极简、纸面、单主角或整齐网格才适合本项目。
- 视觉值集中在 token/共享样式维护是工程约定；token 的值、主题方案与组件样式可以一起重做。复用现有组件是选择，不是设计目标。
- 路径安全、数据一致性、现有功能语义、可访问性和大库性能仍需保证。改布局不会自动授权删除功能、改变 API 或重置用户偏好；设计调整涉及交互时同步更新实现、测试及快捷键说明。

## 产品目标与质量要求

Local Gallery 帮助用户浏览、阅读本地照片、漫画与视频，重点任务是接着看、发现内容、找到目标。页面围绕任务组织，信息主次与操作优先级可因场景而变化。

人物相册列表只展示按照片数降序排列的前 50 个候选组，并说明总组数；照片数相同时按封面资源 ID 稳定排序。人物分析仍覆盖整库照片，列表使用已生成的人脸分组结果计算排名。人物详情的照片墙用双层框标出属于当前候选组的人脸，让用户能在合照中看出该组对应的对象；图例说明框选含义，分组仍不代表身份确认。

当前方案以“照片是唯一的彩色”为视觉方向：界面外壳（画布、卡片、侧栏、描边、遮罩层）全部走无彩灰阶，页面里唯一有彩色的东西是照片本身；衬线标题与照片卡片继续保留书刊感，强调色由主题方案本身决定、不再单独切换。侧栏在明暗两主题下都是画面里最深的表面，靠一条 hairline 与画布分隔。照片侧首页的第一屏是一面照片墙（跨相册随机取的一批照片），其余在读通过有限预览和最近页承接；漫画侧仍是横向阅读区与独立四本未读预览。封面画幅按工作台分侧：照片方形、漫画竖版（4:5）。这是当前设计选择，可继续演进。

后台分析有独立的任务中心（`/tasks`）：四个编号区块顺次往下排 —— 01 运行（当前任务的进度、读数与控制；空闲时这里就是开始分析的入口，等待队列始终显示，空时明确写出当前没有等待任务）、02 任务记录（只显示已完成、失败或取消的任务，可筛选、删除单条或清理全部终态记录）、03 每日计划（开关、时间、已安装模块与默认关闭的人物分析开关）、04 本机存储（派生缓存占用与清理、四个分析模块的模型权重与产物、路径）。运行阶段依次说明 GPU 环境检查、媒体库等待、整理分析清单、准备本机模型与首批推理、持续批量推理。运行区还展示硬件方案：模型任务默认强制使用 GPU，关闭后新建任务使用 CPU；已有排队任务保留创建时的设备选择。GPU 不可用或推理失败时，任务记录原因。清理记录不删除元数据、向量、OCR 或人脸分析结果。进度条的分母是本次任务实际要处理的张数，不是整库规模；预计剩余时间由后端给出。失败项按原因分组，同一原因只留计数，展开才列路径。照片侧地点入口（`/photo/travels`）是一份按时间读的照片日记：抬头分两栏，左边是标题、一行数字摘要（段足迹、去过多少省与市、带位置的照片数、没有拍摄时间的张数）与控件，右边是一块小地图，把照片坐标聚成网格画成点云浮在离线行政区边界上；下面是一条按真实时间比例铺开的时间轴，一格一个月的照片张数画成深浅不一的格子、行程是格子上方的一颗颗小钉，两端各有一个抓手能圈出一段时间；再下面是这段时间里的行程目录（走过多个地方叫行程，只在一个地方叫停留），一行一段，点开才展开照片带与整段的照片；地点详情页 `/photo/travels/place/<区划码>` 给出这个地方的照片、下级地点与到访记录；人物入口（`/photo/people`）用本机相似度形成可改名、合并、拆分和隐藏的候选分组，用户可在照片墙和脸部列表间检查。人物分组不推断身份，地点地图和地名均不请求在线服务。

智能搜索（`/photo/semantic`）先展示中文描述/以图搜图、图片文字和搜索动作；相册、年份、GPS、人物、收藏与精选筛选默认收起，展开后显示当前生效项数。OCR 不要求 Chinese-CLIP，帮助文案说明中文标点、断行归一化与有限的长文本近似修正。照片角标解释结果来自语义、以图或 OCR 精确/近似命中；语义分数仍用于区分相似度，不用颜色单独表达结果类型。

**任务中心是一列，不是一盘棋。** 之前是两栏网格，空队列和空记录各占一格、四千多像素的滚动条里全是空白；现在四段横向铺开，每段自己占满宽度，主次靠段号与留白分，不靠格子。运行段内部再分两栏：左边是这次分析会做什么（模块芯片、一句话说明、当前模式），右边是处理方式与两个动作按钮。

**启动前先给规模，再给按钮。** 用户按「开始分析」之前最想知道两件事：这次要处理多少张、大概要跑多久。以前只有一个「只处理新增或变更的图片」的提示，剩下的全靠猜；跑完一次才发现点了全量，就白等几十分钟。现在运行段在头部条与主体之间放一条「本次规模」：增量与全量两种口径并排列出张数与预计耗时，当前模式那行高亮，两个动作按钮各自带上自己那一份的张数。**两种口径同屏可比**是刻意的 —— 切模式只是换一行高亮，不重新请求，用户能直接看出全量比增量贵多少。耗时来自历史任务的中位速度，**没有历史就明说算不出来**（`estimatedDurationMs` 是空值，不是 0）：一个假的「不到 1 秒」比一句「不知道」更糟。模块不可用（没装、运行时没就绪、人物分析没开）时只说原因，不给数字 —— 给一个假的 0 张比不给更误导。

**选择器摆在明面上。** 分析模块原先藏在下拉框里，打开才知道装了哪些、哪些没装好；现在是一次排开的芯片：就绪的带绿点、选中的高亮、没装的灰着并写明原因。同一类互斥选项（增量 / 全量、展开 / 折叠、照片 / 漫画）统一用分段控件，形状一致，用户看一眼就知道这是二选一。

**磁盘占用属于任务，不属于设置。** 跑完一次全量 OCR 之后磁盘涨了几百 MB，用户要能立刻知道涨在哪、哪个模块的、产物落在哪 —— 这些都是这次任务的后果，所以 04 段紧跟在任务记录后面，而不是让用户跳到设置页去找。04 段分四层：合计与三类占用（媒体派生缓存 / AI 分析产物 / AI 模型权重）、媒体派生缓存的分项与清理、AI 模型与产物的逐模块清单、路径。设置页因此只剩外观与阅读偏好、服务端配置、状态备份和关于 —— 它管「应用长什么样、怎么跑」，任务中心管「跑得怎么样、占了多少」。

**区域靠「白卡套浅色标题条」分层，不靠白卡套白卡。** 一块面板 = 白底 + 一条压浅灰的标题条（标题 + 可选说明），内容在下面。服务端那七组设置之前是白卡里的白卡，只靠一根发丝线分界，整段看不出哪里到哪里；改成每组自带面板、标题做成顶栏之后，一眼能数出有几组、各管什么。区块标题末尾补一条延伸到右边的细线，这一段的内容到这里为止。

**宽屏（24 寸 / 27 寸）上内容要占满，不留半屏空白。** 设置页的短分区在宽屏排两列，服务端那七组面板也排两列；任务中心保持单列，但把宽度用在卡片内部（运行面板左右分栏、每日计划模块与人物开关左右分栏、本机存储两卡并排）。两页都因此短了一半：设置页从五千像素降到两千三。

**导航只有一条竖轴：应用级在侧栏，页面级挂在侧栏里自己的入口下。** 侧栏分两组：上面是当前工作台的浏览入口（照片 / 漫画），下面是「本机」组 —— 任务中心与设置。进了这两个页面，它自己的分区就展开在入口下面（任务中心 → 运行 / 任务记录 / 每日计划 / 本机存储；设置 → 外观 / 阅读 / 数据 / 备份与恢复 / 关于 / 服务端），当前分区随滚动实时高亮，点一下就滚过去。

**之前试过把页面级分区做成内容顶上的一条横条，两条轴并排站着 —— 结果是两条互不相干的菜单：横条在宽屏上是一排孤零零的灰字，窄屏又得横向滚动。搬进侧栏之后导航只有一条轴，内容区也空出了宽度。**

**分区清单只有一份**（`utils/pageSections.ts`），侧栏与页面标题都从它出，两处说法不会对不上。

**路径分两层给。** 相对缓存根目录的路径（`derived/metadata/ocr`、`state/ai_jobs.json`）对所有设备可见，局域网客户端也能看；只有缓存根目录、工作目录、配置文件、Python 环境与各权重文件这类「锚点」的绝对路径限本机浏览器。局域网客户端拿不到绝对路径是预期结果，界面给一行中性说明，不报红。

**任务记录展开时才去取这次任务自己的产物。** 产物目录随任务 ID 走，看一眼就知道结果落在哪、占了多少；折叠状态下不发起请求。批次目录被清理过是正常状态（清人物分析会整目录删掉），界面用灰字说明而不是当故障。

**「缓存」在两页各指一件事，说法要分开。** 设置页的「媒体库索引」是扫描结果与相册摘要；任务中心 04 段的「派生缓存」是浏览与播放时算出来的中间产物（缩略图、预览图、转换图、视频产物）；「分析产物」是各模块的批次结果与索引。同一个词指三件事，用户就分不清自己清掉的是什么。

照片侧另有一套「展陈墙」语言：主角照片裱起来（内白 + 一道细边 + 阴影），网格里的照片裸挂墙上不裱框，页头与首屏那几件主角展品才有框。裱框统一 176px 见方（集合页头、首屏主角、标签页头图），窄屏降到 96px。网格不裱框这一点是截图比出来的：白底卡片把照片挤成中间一小块，说明区又空出一片，整面墙读起来是「一堆白卡片」。

常驻外壳只有两件：顶栏（60px）与侧栏。没有底部状态栏——它的「就绪」是填充文案，秒级时钟对一个本地媒体库没有意义，而扫描进度本来就由左下角的浮动卡负责。库规模与上次扫描时间归到页头，它们是页面上下文而不是全局装饰；顶栏只承担工作台切换、搜索与全局动作。

最近、收藏和未读页使用带场景提示的统一页头；相册与视频详情采用封面、信息和操作相邻的摘要，标签页将标题统计与照片分栏。设置使用一列分组面板与窄屏堆叠表单，阅读器使用中性暗场和浮动控制条，信息面板让开顶部操作。照片工作台没有未读与在读区，漫画工作台才有。两个工作台的基调也各成一套：照片侧冷（冷调品牌点缀 + 方形封面，像展陈墙），漫画侧暖（暖调点缀 + 竖版封面，像书脊）；差异只落在品牌色与 hero 面板底色两处，画布与文字保持中性灰阶。首页首屏同样各成一套：漫画是「继续阅读 / 未读」两块面板，照片是「随手看看」的照片墙加「接着看」一块面板；索引维度一个是年份，一个是作品。照片侧的「最近浏览」是时间线（浏览足迹），漫画侧的「最近阅读」仍是网格 —— 照片没有阅读进度，这一页真正要回答的是「我刚才在翻什么」。所有变化保持原有数据与快捷键语义。

### 相册页的两套页头

相册相关的页面共用一套页头语言，形态有两种：

| 页头 | 用在哪 | 构成 |
| --- | --- | --- |
| `.detail-head` | 集合页（一个集合里的一堆相册） | 裱框封面拼贴 · 眉标 + 衬线标题 + 数量 · 标题行末的收藏 |
| `.album-bar` | 相册详情页（照片墙） | 返回 · 集合 › 标题 + 数量 · 密度 / 收藏 / 更多 |

集合页要给出「里面是什么」的直觉，因此带一条照片带（集合里各相册的照片，轮流取，每一本都露得出来）；封面拼贴只留给漫画侧 —— 那边的封面是书脊与厚度，照片侧的封面拼贴占着一百多像素高，说的却只是「这里有照片」，下面那条照片带说得更准。相册详情页的封面就是照片墙本身，再摆一张封面是重复，因此只留标题条。

照片墙的页头压成一行：返回 · 集合 › 相册名 · 数量，右侧是密度、收藏、更多。照片墙是浏览页，页头占的每一行都是照片的位置；两行式页头在宽屏上还会把标题与控件拉成两个孤岛。所属集合名可点回那个集合 —— 集合名是一段路径，不是一段文字，从相册里得找得到回去的路。

密度切换有四档：自适应 + 三档手动。手动档用方块排布示意疏密（5×4 / 4×3 / 3×2），不写 S / M / L：字母要求读者先建立「字母 = 档位」的对应关系，图形直接说疏密，档位名留在提示与无障碍标签里。自适应档用一块大小不一的版面示意 —— 它没有固定疏密，跟着照片数量与视口变。

**页头的数量与网格里的数量必须是同一件事。** 集合页的网格只列直属子项，页头因此报「直属相册数 + 子集合数」，不报服务端那个包含全部后代的相册总数 —— 两个数字放在同一屏却各说各话，用户只会以为其中一个是错的。父级网格里的集合卡片仍然报后代总数，两处的作用域不同，说法也不同。

**页头与网格共用一条留白线。** 集合页的网格必须待在 `.page-shell` 里，否则卡片会贴到侧栏边上，与页头的左缘差出一截。

**集合页的页头封面按「一本书」处理。** 漫画侧的页头封面是竖版、带装订边、有厚度（`.detail-head__cover--book`），与网格里的书封卡同一套语言；照片侧是裱起来的方形展品（`.detail-head__cover--print`，176×176，内白 + 细边 + 阴影），与首屏主角、标签页头图同一套裱框。眉标也跟着侧走：漫画侧叫「作品」，照片侧叫「集合」—— 与首页的作品索引是同一个词。

**页头封面是这一页的锚点，不能比正文里的卡片还小。** 漫画侧给到 176×220：比网格里的书封卡（168px 宽）更大，四张代表图的拼贴因此每一格都还有内容，而不只是四块色块。四张代表图排成 2×2 —— 容器是 4:5，每格切出来也正好是 4:5，整块读起来是「四本书并排站在架上」。「左边一张通高 + 右边三张窄带」反而把竖版封面切成横条：通高主图被裁得只剩一条，窄带里的三张挤成横图，看着像一面照片墙。

**标签页的头图也是一本书。** 漫画侧的标签页头图此前是照片侧那张摊在桌上的方照（带 3° 旋转），整个漫画工作台里只剩这一处不是书。改成竖版 4:5、装订边与书口齐备、不旋转。窄屏下页头改成上下堆叠 —— 两栏并排时文字栏只剩几十像素，眉标与统计标签会一个字一行；堆叠后头图定宽定高居中，仍是一本书。

照片侧的标签头图则改成裱框照片，不倾斜：倾斜的方照原本是两侧唯一的区别，但照片工作台自成一套语言之后，这枚倾斜成了另一件不相干的东西。

**页头的动作贴在标题这一行的右端。** 列表页（未读 / 最近 / 收藏）的页头右侧本来是空的，动作（随机挑一本）放在那儿既不挤正文，也不会跟描述句读成一串。页头组件因此有一个 `action` 槽位，而不是把按钮塞进描述里。

**集合页知道自己身在哪棵树上。** 页头第一行是「返回」加一条面包屑：祖先集合的名字可点，当前页是大标题不必再列一遍。嵌套只有一层时这一行只挂一个名字，多一层就串成一条。面包屑说的是"你在哪"，「返回」说的是"回去"—— 两件事都要有，缺一个用户就不知道自己是在往回走还是往深里钻。

**集合页的时间线只在真的按年份铺开时才出现。** 多数子集合里的子相册并不带 4 位年份，全落进「其他」桶：一张大年卡加一个「其他」独占一整行，比例失衡，而且这一条索引筛不出任何东西 —— 它是装饰，不是索引。判定标准是**至少两个真实年份桶**，不是「桶数 ≥ 2」（后者把「其他」也算成了一桶）。

**年份卡是照片的入口，不是文件夹的入口。** 照片侧点年份卡直接看这一年的照片：一年散在好几本相册里，先挑一本再进去等于让用户替系统做取舍。漫画侧仍进那一年（那边没有照片墙）。**同一批内容不在两处摆两次**：首页的年份索引已经讲清了按年份命名的那些集合，「库内一览」网格就不再重复摆它们（列表查询用 `excludeYearTargets` 把各年份分组的代表节点去掉；一旦带搜索词或年份筛选，列表仍给出全部命中）。

### 照片侧的几条专属规则

**「最近浏览」排成浏览足迹，不排成网格。** 照片侧这一页的眉标叫「浏览足迹」，内容却是一张普通网格：时间被压到卡片角落的一行小字里，「我刚才在翻什么」答得很含糊。改成时间线 —— 左列时刻（等宽、今天给到分钟、昨天给「昨天 HH:MM」）、中列照片、右列数量，整页读下来是一份浏览日记。时刻用固定格式而不是「N 分钟前」：相对时间会越排越短，读起来像一列长度不一的字符串，排不成一条轴。漫画侧仍是网格 —— 那边有进度与已读状态，网格里已经说清楚了。

**照片墙上的照片是挂着的，不是拼着的。** 图与图之间留 10px，图块带 4px 圆角与一道浅投影，悬停时投影加深。2px 圆角、8px 间距的旧方案读起来是一整块马赛克，照片与照片之间没有边界。

**视频封面裁切填满画幅。** 方形的裱框里保留 16:9 的完整画面会上下留出两条黑边，读起来像一只空信箱而不是一张照片。裁切后它是一张裁过的照片，与图片封面同一套语言。

**年份是一面照片墙，不是一只文件夹。** 「2024 年的照片」散在好几本相册里，入口就该是照片而不是某一本相册：年份墙（`/photo/years/<年份>`）把该年份下各相册的照片铺成一面墙，每张带它出自哪本相册，悬停显示相册名，大图预览的标题点一下就回到那本。年份墙另给出来源集合的入口：照片墙看内容，集合看结构，两条路各管一件事。

**照片墙的密度是算出来的，不是选出来的。** 照片少的时候写死的行高会让整面墙缩在屏幕中间的一小条里，图片显得小；照片多的时候又需要保持密度。默认的「自适应」按数量、比例与视口试排几档行高，在放得下（不超过两屏）的档位里挑照片最大的那一档：照片少时把画面让给每一张，照片多时保持浏览密度，不因为自适应反而更挤。自适应只在「更疏」的方向上动，不会比标准档更密；窄屏另有一行至少两张的上限，容器太窄时不会退化成一列照片列表。用户明确选过手动档之后，自适应不再插手。

**末行与上面的行一样高。** 末行不为了填满宽度而放大（一张图撑满整行看起来像加载失败），但也不该比上面那几行矮一截 —— 高度一致，末行只是没铺满宽度。

**集合页先给照片，再给相册。** 集合页原先只有一张封面拼贴与一排子相册卡，读起来像文件夹管理页：先看图例，再看条目；相册少的时候页面空着一大片。现在页头收成紧凑的一行（照片侧不再摆那张大封面拼贴），下面先给一条照片带：集合里各相册的照片轮流取，每一本都露得出来。照片带同时是快捷入口：点照片开大图，标题写清出自哪本相册，点标题就回到那本。

### 足迹页：右栏一块地图，一条月格纹理带

**照片侧地点入口（`/photo/travels`）是一份按时间读的照片日记。** 它回答两个问题：这些照片是什么时候拍的，那几天我在哪儿。

**抬头只说两件事：这是哪个页面、这个库有多大。** 此前是「裸页头（34/28 像素内边距 + 一整句描述）」「四个 26 像素大数字各自占一格」「贴在最右边的小地图」三块互不相干的东西，加起来约 270 像素，视觉上是三块条而不是一整块。现在抬头是一行：左边眉标与标题，右边一条规模带（主数字加分解），底下是粒度控件。地图不在抬头里 —— 它搬到了正文右栏。

**数字并成一句话，不拆成四个各自占一格的大数字。** 四个 26 像素的数字摊在 880 像素宽的四个格子里，每个数字浮在一大片空白中间 —— 那是「松散」的真正来源。现在是一个主数字加一句补充：**全库照片总数**做主数字（30 像素的 display 字），其余（带位置的、走过多少地方、有多少张没时间）是它的分解，排在一条竖线之后。

**主数字是分母，不是又一个大数字。** 「13,488 张照片 · 全库」给出这一页的分母，「3,091 张带位置」是这个分母里带坐标的那部分 —— 没有分母就看不出覆盖率。

**规模带说的是这个库的事实，不随区间变。** 区间内的数（多少段出行、这些段里多少张照片）报在时间轴的读数里 —— 那里就是管范围的。两处各说各的域：抬头说「这个库有多大」，时间轴说「这段里有什么」。

**描述句删掉。** 口径与误差说明页脚已经有一份完整的，抬头再抄一遍是重复。

**地图升格成正文右栏的一块，滚动时跟着。** 地图承载的信息量最低 —— 一张库里往往只有几个省有照片，全国图里大半是空的 —— 却先后占过整个页面中央、常驻右栏两处版面，两次都被推翻（`3a2f566`、`80e01a6`）。第三次不跟它争版面，但也不把它降级成边缘的一条：它是正文右栏的一块（宽 320–440 像素，随视口缩放），时间轴与行程目录在左边，地图钉在视口里跟着滚 —— 读行程的时候手边得一直有个方位。窄屏上它夹在时间轴与行程目录之间，占满一行。

**地图大了，点云与区划才读得出。** 右栏的地图此前只有 288×144 像素宽，全国图上各省只有几个像素宽，照片位置那层点云几乎是一团噪点。升到三百多像素见方之后，区的深浅与点的疏密才分得出来 —— 地图这块版面买的是「看清去过哪儿」，不是「占住一角」。

**时间轴让出右边一段。** 地图占了右栏，时间轴的宽度就少了一档（1440 宽的视口下约 740 像素）。格子随之变窄，但月份的深浅与空档仍然读得清 —— 这是可接受的取舍：地图是这一页唯一能一眼看完的东西。

**它仍然要密。** 密度的来源只能是用户自己的照片位置：行政区匹配只答得出「落在哪个市」，照片的坐标才画得出城市的样子。因此图上叠一层**点云**：照片坐标按网格聚合成点，一个点是一段约二十公里的范围。底图是去过的行政区（按片数深浅着色），叠上照片的点 —— 从「三十四个色块」变成「我的照片在哪」。

**二十公里一格，是这个尺寸下的唯一选择。** 图只有几百像素宽，几公里的一格在画面里不到一个像素，点会糊成一片噪点；二十公里一格才点得出一颗一颗。格边长只认六档（0.01 / 0.02 / 0.05 / 0.1 / 0.2 / 0.5 度），是「画多细」的档位，不是一个连续参数。点的大小按屏幕像素算，不随缩放走 —— 放大地图时点不会糊成一坨。

**画面裁到照片真正在的那一片，而且不切边。** 行政区比照片的位置大得多（一个市几百公里，照片往往只在市区那几公里里），按行政区裁会裁出一大片空白；按照片裁才是一张「我的照片在哪」的图。裁的时候取「内容整个留下」而不是「画面装满内容」—— 这个尺寸下宁可两边留白，也不要切掉最远的那几张照片。

**地图有两种范围：只看有数据的，和整张的。** 缺省是「有数据」—— 画面裁到照片真正在的那一片，读者一眼看到的是「我去过的那一片」。但那一篇之外的国家是什么，读者看不到，而「去过的地方在全国的哪儿」这个问题只有整张图答得了。地图上方那条窄栏里有个二选一（`有数据` / `完整地图`），切到完整地图就不再裁，整张中国铺满画面。

**完整地图里，没去过的地方要铺成底图。** 只画有照片的那几个省，整张地图看上去就是空白里几个色块，看不出那是哪儿 —— 去过的地方按张数深浅，没去过的地方铺一层极淡的底色加一道省界，整张地图才读得出形状。

**点云只以网格下发。** 一格是一段范围，格心不是照片坐标的平均值 —— 一格里到底有没有照片，图上看不出来，也不该看出来。响应里没有资源 ID、没有路径、没有单张照片的经纬度。

**地图不提供操作，也不提供点击。** 一块几百像素宽的图上，一个市只有几个像素宽，拖不动也点不准；给它做平移缩放与逐个区划的键盘焦点，是给一个没人会用的控件写契约。要去某个地方，从行程卡片上的地点链进 —— 地名才是能读的东西。

**时间轴是一排月格，不是一条曲线。** 逐月的张数是离散的量，格子才读得出确切是多少，也读得出空档：曲线把「那几年没怎么出门」抹成了一段缓缓的斜坡。格子没有这个问题 —— 一格一月，深浅是那一个月的张数，没有照片的月份淡到几乎看不见，那几年的空档一眼就跳出来。

**为什么不用曲线。** 此前试过：逐月的张数画成一条平滑的曲线，行程是线上的一颗颗珠子。曲线读起来是「一段起伏」，但它说不清某个月拍了多少，也把空档抹平了 —— 2014 年与 2016 年之间的那段缓坡，读者无从判断是「没出门」还是「出门少」。格子把这件事说清楚了。

**为什么不是三层叠着。** 更早一版把逐月的密度直方图、行程块、刷手轨道分作三层叠着，每层各说各的，读起来像三张图表拼在一起。现在合成一件东西：格子上方那一排小钉是行程，其余是密度。

**行程是格子上方的一颗颗钉。** 每段行程钉在它开始的那个月，点它选中那一次出行。同月多段时横向错开。钉有 28 像素的命中区，够手指点也够键盘聚焦 —— 看得见的那几像素不是命中区。

**两种记号就要有图例。** 格子上方是行程、格子里是张数，各是一种记号，因此标题行给一行键（`▉ 每月张数  ▲ 行程`）。文字用文字色，不穿数据色。

**确切的值报在标题行的读数里。** 悬停某一格，那一格描一圈，标题行右侧的读数换成「2019-05 · 42 张」；悬停一颗钉，读数换成那一段的日期、地点链与张数。不做浮在图上的提示框 —— 浮框要么被横向滚动容器裁掉，要么盖住别的记号；读数行位置固定，永远看得见。

**时间轴按真实时间比例铺开。** 月份占一个位置，稀疏的年份自然拉开、密集的年份挤在一起，一眼看出哪几年在出门。空档的月份也要占位 —— 少了它们，稀疏的那几年会被压扁，看不出那几年其实没怎么出门。

**默认只画最近五年。** 十几年的历史一次铺开，一格一个月会细到读不出来；默认给最近五年，一格约二十像素，月份与深浅都读得清。想看更早的按「1年 / 3年 / 5年 / 10年 / 全部」—— 跨度锚在有照片的最后一月，往回数的五年。跨度写进地址的 `span`。

**换跨度就是换了一个范围。** 跨度按钮换的是轴的范围，也换下面的行程目录与地图上的点；刷手圈出的区间会一并清掉 —— 旧区间留在新范围里会打架。刷手仍然能在范围内圈一段更细的区间。

**区间里的数报在时间轴的读数里。** 「最近 5 年 · 10 段出行 · 2,312 张」：抬头管库的事实，时间轴管当前范围，两处各说各的域。

**时间轴是全局的那把尺子，区间只是尺子上的一段高亮。** 区间之外压暗但仍然留着（蒙版，不是删除）—— 位置稳定，读者知道「那段在外面」。一拖手柄尺子就缩的话，「我在整条历史的哪个位置」这件事反而丢了。

**两端各有一个抓手，拖它圈出一段时间。** 抓手是一根发丝线加一个底部的圆钮，不是一条粗柱 —— 粗柱在带子两端看着像滚动条。轴上拖动：从按下处起一个窗口，拖到哪里圈到哪里；已有窗口时，拖窗口内部整体平移，拖窗口外把最近的那一端拉过来。区间写进地址的 `from`/`to`（`YYYY-MM`，缺省＝全部时间），换粒度、下钻、返回都带着它。丢了区间就等于把「2019 年在杭州」这类叙事掐断在一次点击上。

**行程按两周的间隔切，区分「行程」与「停留」。** 相邻照片的日历日间隔超过两周才算另起一段：一段里走过多个地方是「行程」，只在一个地方的是「停留」。两天的口径是「回来算又一次到访」，拿来做行程会把出门一趟切成好几段（实测 265 段），两周的口径是 28 段 —— 一份读得完的日记。**「在江西待了两年」是一句实话，写成「行程」就成了假的移动**，所以停留单列，不套地点链。地点链按顺序排开（`杭州市 → 丽江市 → 大理白族自治州`），一行读完是一次出行。

**行程不随时间区间重切。** 段是切出来的，照片按段的下标寻址 —— 段若随区间重排，下标就再也指不到同一段照片了。因此行程列表与行程照片端点都不带区间，刷选与跨度只决定哪些段被点亮、地图与地点清单过滤到什么范围；抬头那条规模带说的是全库的事实，不随区间变。

**行程目录按年份倒序，两栏并排。** 年份由近到远排：最近的一段排在最前面 —— 读者多半是在看最近去过哪儿。一段行程收着的时候只有两行高（日期与张数一行、地点链一行），一列排下来整页读起来是空的；两栏并排，一屏能读到的段数翻倍。窄屏（<640 像素）退回一列。

**行程是一张卡片，不是一行。** 卡片有自己的底与边，收起时两行：第一行左边是日期区间、右边是类型与张数；第二行是地点链（`杭州市 11 › 湖州市 5 › 上海市 9`）。地点链收起时只摆前四个，其余收成一句「还有 N 处」；展开时整条链都摆出来 —— 一次出行串十几个地方，全摆出来卡片会高得读不成一行。

**点开才展开照片，展开的那张横跨两栏。** 点开才给照片带与整段的照片墙；横跨两栏是因为照片带与照片墙在一栏里摆不下。**同时只展开一段**：每段都能各自展开的话，整页长度不可控，几百段就是几万像素的滚动条 —— 那正是这一页此前最不好用的地方。

**照片按需取回。** 一段的全部照片在用户展开那一段、或点开带上的某一张时才去取 —— 一次读回三十多段的全量照片既慢又没人看。段头给出一段的照片带（至多十二张，按时间均匀取样，含首末），它已经足够说明这一段的内容。

**悬停一段行程，底下浮出一张轨迹图。** 卡片上摆着的是「这一段是什么」，轨迹图回答的是「这一段怎么走的」：一张小地图，去过的地方画成轮廓，按次序连成一条带箭头的线，每一站标着序号（1、2、3、4），下面一张站点表给出每一站的地名、日期与张数。焦点落进卡片时同样浮出 —— 键盘用户也能看到。

**浮层要够大，地图才看得全。** 浮层宽 460 像素，地图的画布是 420×220（窄屏上退到卡片宽度）。第一版只有 340 像素宽、300×160 的画布，地图小得看不清一个省的轮廓。

**视野按轮廓算，不按落点算。** 行政区比它的重心大得多 —— 一个市几百公里，照片位置往往只在市区那几公里里。按落点裁会把边缘切掉一半，地图看着像缺了一块；轮廓与落点一起算，才看得全这一段去过的地方。

**卡片靠下时浮层往上翻。** 浮层比卡片高得多，卡片贴着视口下缘时往下展开会掉出屏幕 —— 那时候翻到卡片上方去。

**轨迹图连的是行政区里的落点，不是真实路径。** 它读的是「按顺序走过这些地方」，不是「沿哪条路走的」；站点表与序号把这句话说死，不必再加解释。

**同一个地方反复到访，标记错开摆。** 一次出行常常在两三个城市之间来回 —— 标记叠在一起就只剩一个点，次序读不出来。错开摆成一小圈，一圈标记对应一个地方，看得出「又回了一次」。

**箭头摆在段中间。** 摆在末端会被下一站的序号圈盖住，方向就读不出来了。

**通栏，不留半屏空白。** 产品主要跑在 24 寸与 27 寸显示器上，内容应当占满可用宽度：足迹两页用通栏容器（左右各留一档随视口缩放的边距），不套进带上限的窄壳。照片墙类页面本来就该如此 —— 一张照片旁边还空着半屏灰地，等于把它缩小了。

**先给规模，再给位置。** 抬头左边是标题，右边是一条规模带（全库照片总数做主数字，带位置的、去过多少省与市、没有时间的张数跟在一条竖线之后）。这些数是同一句话，并成一条读；拆成四个各自占一格的大数字反而读成四件独立的事。

**地方是导航，不是筛选。** 去某个地方有两条路：行程卡片上的地点链，或地点详情页。地图上认不出「杭州还是绍兴」，所以地点链上的地名是能点的文字 —— 想看「在哪儿」看地图，想按名字找就从地点链进。

**大地图上不画行踪折线。** 它连的是行政区质心，画出来是示意而不是真实路径 —— 在一张「去过哪些地方」的地图上加一条假路径，只会让人以为那是走过的路。要看次序，看悬停浮出来的那张轨迹图：那里有序号与箭头，读的是「按顺序走过这些地方」。

**到访按日历日切。** 同一区域的照片按拍摄时间排序，相邻两张的日历日间隔 ≤ 2 天算同一次到访（跨夜行程算一次），超过则另算一次。按日历日而不是按小时，是因为「晚上八点和第二天早上八点」在人看来是一次。列表与照片墙共用同一个切分函数，不会对不上。

**诚实说明数据质量。** 库里约四分之三的定位来自基站与网络，不是 GPS 芯片 —— 归属可能有百米量级偏差，页面底部写明。没有可信拍摄时间的照片（解析不出、年份明显不对）照常计入空间统计，但不进时间带与行程，统计行如实写出张数。它们**仍然画在地图上**：位置是真的，只是不知道什么时候 —— 一并丢掉的话，一张没设时钟的照片就会让整张地图空掉。

**窄屏上时间带横着滚，地图压扁。** 时间带不折行（折行会让「哪几年拍得多」这件事看不出来）；跨度太长时按固定宽度排，条带横向滚动。窄屏上正文变一栏：时间轴、地图、行程目录依次往下排，地图压到约 46vh。

**地点详情页用照片墙的身份条。** `/photo/travels/place/:adcode` 的页头是地点的代表照、名字与统计，下面是照片本身、下级地点与到访记录 —— 从一个地方继续往下走，不必回到总览。页面通栏，照片墙因此能铺满整屏。下级地点按真实层级给出（省下面同时挂着地级市与省直辖县级区域，两种都列），横排成一行入口，一眼能看完。到访记录常常上百条，每一条都能就地展开看那几天拍的照片 —— 一次全取既慢又没人看。

**地点详情页页头带一张位置图，不是分布图。** 分布图回答「哪里拍得多」，位置图回答「这是哪儿」：画全幅的上一级轮廓，只有当前这个地方着品牌色，其余全是中性底。裁到内容会只剩这一个省，反而失去「在哪儿」的意义，所以这张图不裁、也不给切换；它是定位用的，不做成可点的入口 —— 点旁边那块灰的省跳去那个省，是读者不会期待的动作。

**能力边界要如实说。** 离线边界覆盖省、市、区县三级；台湾省没有可用的市县边界，按叶子处理。省的下一级可能同时包含城市和省直辖县级区域，副标题按实际区域级别标注；城市下有区县时可继续下钻，没有下级边界的区域直接落到照片墙。页面说明当前使用 AreaCity 2026 年 4 月版数据、主要来源与 GCJ-02 坐标系，乡镇边界不包含在内；坐标与边界都在本机处理。

### 照片级的精选

收藏是相册级的：收藏一本相册，收藏的是「这一本值得留着」。精选是照片级的：
精选一张照片，说的是「这一张值得留着」。两者是两份数据，界面上也必须说得出
两者的差别 —— 用户不该以为「我把相册收藏了，里面每张也都是精选」。

**两种标记在形状与颜色上都分开。** 收藏用琥珀色的星标（`--favorite`），精选用
黑底白勾的圆点（照片墙角标、侧栏入口、批量操作条都用同一枚圆圈加勾）。
星标是「一整本」，圆圈加勾是「一张」。颜色上精选刻意不走 `--favorite`：
收藏是全局一份数据，它的颜色也不跟工作台模式走；精选另起一套颜色会让
「同一个琥珀色表示两件事」。精选角标本身是中性黑白 —— 照片是页面上唯一的
彩色，精选标记不该去抢照片的注意力。

**角标不常驻。** 满墙都是圆点会把照片本身挤掉，墙上挂的是照片，不是标记。
未精选的角标悬停才浮出来（一个加号），已精选的一直挂着。

**多选时让位。** 进入多选后，角标的位置换成方形的勾选框：圆形是照片的常驻
状态，方形是这一轮的操作状态，形状与配色都分开，用户不会把「这张在精选里」
和「这张被勾上了」看成同一件事。勾选框与角标的按钮本身都是 28px 见方，
角标看着小，但小到 20px 的目标在触摸设备上几乎点不中。

**精选页要能回到原处。** 精选页的照片来自不同相册，大图预览的标题给的是
这张的出处，并且是链接：点一下就回到那本，看得见它在一堆照片里的位置。

**并排对比共用一把尺子。** 两侧同时缩放、同时平移：要比的是同一档放大下的
细节，两边各自缩放就失去了可比性。底部只有一处缩放读数，就是这个意思。
对比浮层开在大图预览之上时，预览不接按键 —— 两层浮层不抢同一个键。

### 两侧的词

叶级目录两侧都叫「相册」，集合词分侧（照片「集合」/ 漫画「作品」）。照片侧原先把这个东西叫「文件夹」，而计数单位、集合页头、标签页统计、属性弹窗都叫「相册」—— 一个东西两种叫法，用户要记两套。计数说「本相册」，漫画侧说「卷」。


| 设计维度     | 自主决策空间                                 | 验收关注                                                                                         |
| ------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 信息架构     | 区块顺序、导航形式、搜索位置、分组与内容密度 | 用户能理解页面并找到高频操作，信息与动作相邻，重复入口有实际用途                                 |
| 视觉语言     | 色彩、排版、图形、表面层次、留白与动效       | 形成有辨识度且连贯的表达，文字层级可读，视觉重点与当前任务一致                                   |
| 响应式布局   | 流体或限宽容器、不同页面的网格、列数与断点   | 宽屏空间利用合理，窄屏仍有完整操作路径，没有意外溢出、遮挡与失衡空洞；不要求所有页面内容左缘相同 |
| 媒体呈现     | 不同画幅、裁切、陈列、视频与图片的区分方式   | 重要内容保留清楚，大图分辨率足够，失败有解释，不改写用户原始媒体                                 |
| 阅读器       | 画布明度、控件位置、常驻或按需出现的层次     | 阅读舒适，控件容易发现且不挡翻页热区，图片/视频操作及偏好恢复正常                                |
| 主题与无障碍 | 重做视觉 token 与主题表达、键盘和触摸呈现    | 明暗主题均可读，文字/图标对比度达标、命中区足够、焦点可见，支持减少动态效果与离线使用            |

阅读器的控件分两层：**位置信息常驻**（顶部条与底部页码进度条），**操作入口按需出现**（底部浮动工具条空闲后淡出，鼠标靠近底部或按下任意键就回来；左侧跨卷导航同理）。画布是主角，控件不该一直压在它上面；但「现在读到第几页」永远不需要先找到工具条，所以淡出的只是操作入口，不是位置信息。

**顶栏是两块浮层，不是一条通栏。** 通栏浮层会一直压住画面顶端 —— 漫画页的上缘因此永远看不见，而「这一页从头到尾都在屏幕上」是阅读时最基本的一条。拆成左侧（返回 · 书名 · 页码）与右侧（工作台 · 收藏 · 全屏 · 更多）两块之后，中间留白直接透到画面上，点空白处还能翻页。左侧那块贴着内容收紧：书名短时浮层就只有那么宽，画面上留出来的空隙才真的空。

**顶栏的书名带作品。** 漫画的卷名只写「第1卷」：顶栏只写卷名时，这一卷属于哪部作品看不出来。作品名补在卷名之前（"星海漫步 · 第1卷"），与书封上的写法一致 —— 翻开一本时，这一行该说的是「我在读哪一部的哪一卷」。

**画布给常驻控件留出两条带。** 顶栏与底部页码条是不淡出的，压在画面上就等于永久遮住这一页的开头与结尾 —— 而漫画页的头尾正是最不该被遮住的地方。画布因此上下各让出一条（`--reader-chrome-top` / `--reader-chrome-bottom`），页面永远落在两条带之间。同一原因，「按高度适配」在阅读器里参照的是画布高度而不是视口高度。

**双页并排时每一页都要落进画布。** 竖版页按半宽铺开会高出画布，上缘被切掉，读者看到的是页面中段而不是这一页的开头。并排行的子容器要撑满行高（`items-stretch`），图片的 `max-h-full` 才有确定的参照高度。

加载、读取失败、资源失效与筛选为空应可区分；未读/在读/已读来自真实数据，表现形式可重新设计。异步操作保留已加载内容与已确认结果，错误可重试。模态隔离、焦点恢复、快捷键与触摸操作是交互质量，不限定组件外观或固定位置。

**「这一侧没有内容」与「整个库还没内容」是两种空态。** 媒体根可能全被设成漫画属性，照片工作台一部都没有，但库本身是扫过的。两种情况的引导不一样：后者是「首次使用请先设置媒体目录」，前者是「去设置里改属性，或者先去另一边看看」。混成一句话就把人指到了错误的地方。

**空态一律带图标。** 图标画在两本书之上（`.empty-state__icon`），是整个界面里唯一一处「书」的示意，收藏、未读、标签、相册各自的空态都用它 —— 有的空态有、有的没有，页面就像还没做完。图标按语义选：找不到东西用「文件夹 + 放大镜」，筛选后为空用漏斗，收藏用星标，最近用时钟。

**属性面板用规格表，不用堆叠。** 标签在左一窄列、值在右、行间一条分隔线 —— 阅读器的图片信息面板与相册的属性弹窗共用这一套。堆叠写法（标签在上、值在下）八个字段就把面板撑到近 600px 高，下面大半是空的，而规格表本来就该横向扫读。

**规格表的标签跟着侧走**：漫画卷写「页面 10 页」，照片写「图片 10 张」—— 漫画侧写「图片」再配「页」是自相矛盾的。卷还要单独一行「所属作品」：属性表里只有「第2卷」时，这条记录讲不清是哪一部的哪一卷。

### 业务日期的口径

相册与集合对外只有一个「日期」，它按**文件名 → 目录名 → 文件修改时间**三级取：

| 来源 | `dateSource` | 什么时候用 |
| --- | --- | --- |
| 文件名 | `filename` | 文件名里带得出拍摄日期（`IMG_20240101_…`、`2024-01-01`、中文前缀 + 日期数字），且这个日期在该相册的多数文件上成立 |
| 目录名 | `folder` | 目录名里带得出日期（如「2024年」「2024-01」），但没有文件能证明拍摄时间 |
| 修改时间 | `modified` | 两者都取不到，退回文件修改时间 |

**只有照片侧有拍摄时间。** 拍摄时间从文件名推断，不读 EXIF、不额外读盘；漫画侧没有这个概念，那边的「加入时间」是目录日期与修改时间。排序项因此分侧命名：照片侧「按拍摄时间」，漫画侧「按加入时间」。

**「没有时间」是一种状态，不是公元 1 年。** 后端零值时间序列化成 `0001-01-01T00:00:00Z`，前端把它归一成缺失（`utils/date.ts#usableDate`），否则按时间排序时它会永远垫底，看起来像「最旧的那本」而不是「不知道什么时候的」。

**日期必须能代表它代表的东西。** 一本相册的 `date` 是它内部出现过的拍摄日期里的**众数**（按媒体数加权，并列取较早的一个），集合的日期是它后代相册日期的众数 —— 「这一本是什么时候的」不能由某一个文件说了算。「那年今日」命中的是具体某一天，因此每项另给 `matchedDate`；相册的代表日期与命中的那一天不是同一件事。

### 视觉系统：字号、圆角与语义色

视觉值只有一份来源：`tokens.css` 定义，组件不写死数值。Tailwind 的 `borderRadius` / `fontSize` 映射到同一批 CSS 变量，因此 `rounded-lg` 与 `var(--radius-tile)` 指的是同一个值。

**字号阶梯**（`--text-*`）每一档只承担一个角色：

| 档 | 值 | 角色 |
| --- | --- | --- |
| `--text-badge` | 11.5px | 徽章、键帽 —— **只允许拉丁字母与数字**；带汉字的徽章（转码状态、标签、导航分组名）一律升到 `--text-meta` |
| `--text-meta` | 12.5px | 次要信息：时间、来源、计数 |
| `--text-body` | 14px | 正文、元信息行、按钮与输入的文字 |
| `--text-label` | 16px | 卡片标题、列表行标题 |
| `--text-section` | 21px | 区块标题 |
| `--text-page-sm` | 28px | 次级页标题：最近 / 收藏 / 未读 / 设置 / 标签 / 相册 |
| `--text-page` | 42px | 工作台首页标题 |

中文正文不低于 12.5px。原先卡片标题停在 14px，与区块标题 21px 之间空着一档，标题撑不起视觉锚点 —— `--text-label` 就是补上的那一档。随视口缩放的展示字号（hero 标题、相册摘要标题）用 `clamp()`，两端是唯一允许的硬编码。

**圆角阶梯**（`--radius-*`）按形状命名而不是按大小编号：编号式命名会让同一个数值在不同语境里被当成不同含义，于是组件里开始出现 11px / 14px / 18px 这类硬编码。`--radius-xs` 4 / `--radius-media` 8 / `--radius-control` 12 / `--radius-tile` 16 / `--radius-panel` 22。书脊造型（品牌方块、漫画封面、空态图标）的非对称圆角是造型不是尺寸，单独注明。

**语义色分工**：`--brand` 跟着工作台模式走（照片冷、漫画暖），只出现在品牌标记、页眉眉标、章节序号、焦点环与卡片标题的悬停态。`--favorite` 是收藏专用色，**不跟模式走** —— 收藏是全局一份数据，颜色也该全局一致；它同时避开 `--warning`（扫描告警）与 `--brand`，否则「琥珀色」会同时意味着三件事。`--warning` 只表示扫描与加载告警。

**压在品牌色上的文字色也是一份 token**（`--brand-contrast`）：品牌色跟着主题与工作台翻明暗（浅色主题是深暖褐 / 深墨蓝，深色主题是浅暖褐 / 浅墨蓝），压在它上面的字必须跟着翻。Tailwind 侧也要映射这一项 —— 少了映射，`text-brand-contrast` 这个工具类根本不存在，元素会退回继承的正文色：浅色主题里近黑压深蓝（2.6:1），深色主题里近白压浅褐（1.5:1），顶栏的模式切换按钮在两套主题下都读不清。**颜色 token 要么在 Tailwind 里映射，要么就别在组件里用它** —— 工具类不存在时不会报错，只会安静地不生效。

悬停与焦点同源：焦点环用品牌色，是因为「焦点属于当前工作台」；卡片标题在悬停时也换成 `--brand-ink`，理由一样 —— 这一下动作发生在哪个工作台里，就带上哪个工作台的色。两侧的色都压得住灰阶画布（照片侧是墨蓝、漫画侧是赭褐），不会把照片的彩色抢过来。

**焦点环**：用 `--focus`（即品牌色）而不是 `--accent`。`--accent` 在浅色主题里是近黑的石墨色，压在深色照片上就是一条看不见的黑边。焦点环不写 `border-radius` —— `outline` 会自己跟随元素的圆角。

**两个工作台的材质**：光靠品牌色区分两侧还不够 —— 换过去看着还是同一个产品。材质让它们真正分开，靠一组按 `:root[data-mode]` 覆盖的 token：

| token | 照片侧（展陈墙） | 漫画侧（书架） |
| --- | --- | --- |
| `--card-bg` / `--card-border` | 透明 / 透明 | 透明（书自己就是那件东西） |
| `--card-radius` | 6px | 16px |
| `--card-shadow` / `--card-lift` | 无 / 0 | `--shadow-md` / −3px |
| `--panel-bg` | `--bg-elevated`（白展板） | `--feature-bg`（暖纸） |
| `--hero-cover-col` | 176px | 168px |
| `--section-index-font` | 等宽（展陈的现代感） | 衬线（书刊感） |

照片侧的照片才是主角，卡片不画框也不浮起；漫画侧的每一本都是一件独立的东西，封面自己带装订边与厚度。

### 漫画侧的书封

漫画工作台是书架，每一张相册卡都是「一本书」而不是「一张图片加一段说明」。这套书封语言落在四个地方，缺一处，两侧就会重新长成同一个产品：

| 构件 | 做法 |
| --- | --- |
| 封面上印着书名 | 标题压在封面的下缘（`.cover-title`），近黑实心渐变保证白字在任意封面上都读得清；封面下方不再重复标题 |
| 作品名印在书名上方 | 卷名只写「第1卷」时，一屏里两本「第1卷」分属不同作品，光看封面分不出谁是谁。真实书封就是这么排的：作品名（`.cover-title__series`）在上，卷名在下；两者相同时不重复印 |
| 装订边 | 封面左侧的内侧阴影 + 右侧更大的圆角（`.album-tile__cover--book`），与首页 hero 的书形封面同一套轮廓 |
| 厚度 | 封面自带投影；悬停时书从架上抬起 4px，标题留在原位（像抽出半寸） |
| 画幅 | 竖版 4:5（`coverRatioForMode("comic")`）|

书名印在封面上之后，封面下方的说明区只剩一行计数与进度，读起来是「书脊下的标签」而不是「图注」。这一下同时消掉了旧版网格里的两个毛病：说明区要给标题预留两行高度，短标题下面空出一段空洞；一屏里几十张卡的说明区参差不齐。

**卷名处处带着作品名。** 只写「第1卷」时，一屏里两本「第1卷」分属不同作品，光看封面分不出谁是谁。因此凡是出现卷名的地方都补上所属作品：书封压条、列表行、侧栏续读卡、悬停预览、阅读器顶栏、属性弹窗、跨卷提示与首屏续读队列 —— 同一批数据，界面上只有一种说法。

**4:5 而不是更瘦的 2:3**：书架上的书脊确实瘦，但封面一旦太瘦，横向素材会被裁掉一半以上 —— 裁剩的那一条既认不出内容，也不像一张封面。4:5 仍是竖版（与照片侧的方形分得开），却能留住画面里真正有信息的那部分。照片侧保持方形展陈，两侧一眼能分辨。

**卡片密度随画幅走**：竖版封面本身窄，再按展陈墙的列宽（210px）铺开，每张卡会撑成一张巨幅海报，一屏只看得到四本。漫画侧用更密的网格（`.library-grid--comic`，列宽下限 168px），一排六到七本才读得出「一排书」。

**词跟着侧走**：集合在照片侧叫「集合」，在漫画侧叫「作品」—— 首页的作品索引也是同一个词。两处用同一个词，用户才认得出这是同一类东西。

**索引条上的次级按钮不常驻**：索引卡右上角的筛选按钮常驻时，读起来像两本书之间夹着一个不相干的控件，一排索引的节奏也被这几个白方块打断。指到哪一年再浮出来；正在筛选的那一年一直留着（它要负责取消筛选）。

**年卡报的是照片量。** 「1 本」对谁都没有信息量 —— 首页的年份多半对应一个同名集合，直属子项恒为 1。年卡改报这一年的照片数（「3511 张」）；照片数与视频数一起写会折行，只报照片。

**多图拼成的封面按画幅拼**：一本书常常没有单独的封面图，只能拿同一本里的几张内页拼。这种拼法跟着画幅走：照片侧的方形封面把两张竖着切、三张切成「一张通高 + 右侧上下两块」；漫画侧的竖版封面反过来 —— 两张上下切（每块接近横图），三张切成「上面一张大图 + 下面两张并排」。竖版封面若沿用方形那套，两三张会被压成认不出内容的细条。

### 筛选条

列表页与网格页共用的那条筛选条（视图 chip / 最少图数 / 排序 / 网格-列表）只有一条规矩：**一排等高的控件**。视图 chip 与排序按钮是 34px，最少图数与视图切换也跟着 34px —— 高度不齐时，一排控件像没对齐的积木。

网格 / 列表是一条**分段控件**：轨道有底色，选中的那一段抬起来成为白底深色字（与主题切换同一套语言）。早先两个 30px 的方块各自带一圈边框，激活态只是把底色换成 `--bg-subtle`，在浅色画布上几乎看不出差别 —— 两个图标悬在筛选条右端像两枚散落的方块。

**首屏面板只有一种**：照片侧首屏原先同时出现两种底色 ——「接着看 / 随手看看」一种，「最近加入」另一种，两个工作台自己就不成套。现在统一为一个 `.hero-panel`，表面从 `--panel-*` 读；漫画侧整屏是暖纸，照片侧整屏是白展板。照片墙本身不套面板：照片直接挂在画布上，套一层白展板就又变成「关于照片的说明」。

**首屏两块面板同一种语言**：漫画侧首屏是「继续阅读 | 未读」两栏，右栏「未读」的四张预览卡用竖版书封（4:5），与网格、页头封面同一套画幅 —— 早先用 4:3 横幅，右栏因此比左栏矮一大截、底下空一大片纸，两块面板读起来像两个产品。改成竖版之后右栏自己长到与左栏齐平，等高不再靠拉伸凑。

**面板里的总数与摆出来的数要能对上**：漫画侧「未读」面板标题写的是未读总数，网格只摆四本预览 —— 差额写一行「还有 N 卷没读」，与「继续阅读」面板的「还有 N 卷在读」同一套写法。否则读者会以为少渲染了两本。

**首屏两块面板必须等高**：等高是结果，不是靠拉伸凑出来的 —— 一栏靠拉伸填满，栏内就会空出一大片纸，视觉上仍然一高一低。照片侧现在只有一块面板（照片墙不占面板位），这条规则因此只约束漫画侧。

**漫画侧首屏那本书是主角**：封面给到 260px（照片侧的裱框是 176px）。200px 时它在宽栏里像一张缩略图，底下还空出一大片纸；260px 时它才像从架上抽出来的那一本。

**窄屏上的书封不能把文字压没**：漫画侧按侧覆盖的封面列宽（260px）在手机上只剩三十几像素给文字，「上次，看到这里」被挤成一列单字，按钮还溢出到屏幕外。手机上这一列收回到 108px，与照片侧同一尺寸。

**照片侧的「接着看」独占一行，主角与队列并排**（1280px 起）：这一块面板通栏时，主角那一行右侧会空出一大片，队列却掉到下一行把面板拉高。主角与队列并排之后，面板回到「一块展品」该有的样子。

**队列排成一排小方照，不是一列三行。** 一列三行只占住面板的右上角：主角与队列之间空一大片，右下也空一大片，整块面板读起来像半张空纸。改成一排之后，主角那枚裱框方照与三张裸挂的小方照是同一面展陈墙上的四件展品 —— 主件裱框、次件不裱 —— 面板右边不留空洞。「还有 N 本最近看过」写在标题行右侧：放在面板底部时，底部左侧空着、右侧飘着一行字，读起来像漏排。

**「那年今日」的照片摊满整行。** 固定六列时，四条命中就在行尾留下两列空白，一段关于回忆的入口读起来像缺了东西。列数随命中数自适应（每张 160–260px），行因此始终是满的。

**首屏阅读顺序宽窄一致**：照片侧文档顺序固定为「随手看看（照片墙）→ 接着看」，宽窄屏一致。宽屏与窄屏的顺序必须一致，否则同一份内容换个宽度就读法不同。

**照片是第一眼看见的东西。** 照片侧首屏先摆照片墙，再摆「接着看」：「接着看」说的是「回到上次那本」，是任务；照片墙说的是「看看有什么」，是内容。任务型入口压过内容型入口时，用户打开首页看见的是关于照片的说明，不是照片。「最近加入」不再单独占一节 —— 它与下方网格是同一批内容，网格按「按加入」排序就是它。

### 阅读进度

**轨道要短**：进度条占满一整行时，空的那部分读起来是分隔线而不是进度条 —— 而漫画工作台里绝大多数书还没翻开，空轨道是常态。轨道给固定宽度（列表行 80px、侧栏卡片 56px、首屏 160px），旁边跟着页码读数。

**空轨道不出现**：列表行里那条永远空着的灰条压在短标题下面，读起来是标题的下划线，不是进度条 —— 它说的「还没翻开」已经由标题行上的未读标记承担，不必再说一遍。首屏续读卡、侧栏卡片、列表行与悬停预览是同一套规则：轨道只在真有进度时出现，网格卡片上同样只在有进度时给读数。

**同一行里不并列两个口径的数**：首屏的「读到 1 / 24」说的是翻到第几页，「已读 0%」说的是离结尾还有多远 —— 两个数并排会互相打脸（读到第 1 页，已读却是 0%）。只留页码，百分比交给下面的进度条表达；网格卡片上只有百分比、没有页码，两者不冲突。

### 目录浮层

阅读器的目录（`T` 键）是一整屏的缩略图网格，要回答两个问题：「现在在第几页」和「那一页在哪」。因此页头要有层级（标题、页数、怎么关），当前页要一眼认出来 —— 页码反过来印成白底深字，一屏几十张缩略图里只有这一张跳得出来；缩略图取不到时（解码失败、格式不支持）留一块底色与页形记号，而不是一个空着的黑格子 —— 那个看着像页面没加载出来。

### 读完的收尾提示

读完一卷后弹出的收尾提示（「这卷读完了 / 下一卷 / 回到相册」）与底部浮动工具条都在底部居中，两层不能叠在一起：提示压住工具条、工具条从提示底下露出半截，像两层没对齐的浮层。提示落在工具条之上（`bottom-28`，工具条是 `bottom-[52px]`），两层各归各位。

### 视觉验收

- 每次优化完成代码调整后，重新构建并启动当前源码版本，再截取受影响页面的实际运行画面；逐张检查并记录发现的问题，修正后重新构建、启动和截图，直到截图反映最终代码。非界面优化也遵守通用规则，至少启动最新版本并截图确认运行状态。
- 先说明这次设计要改善的用户体验和视觉方向，再用实际页面验证。避免把“加大封面、排列卡片”当作全部设计，也不要仅为填空白增加无关模块。
- 从完整页面判断信息结构、主次、图文比例、密度、留白节奏与跨页连贯性；允许有意图的非对称和不同页面布局。旧截图用于对比问题，不要求像素还原。
- 使用横/竖图、视频、长标题、少量/大量内容及空态等真实数据状态检查方案，不能只在理想样本下成立。
- 宽度要一起看。断点规则里的特异性陷阱（外层的模式专属规则压过内层的窄屏规则）只在窄屏上暴露：首屏被压成两栏、标题挤成一列竖排的字。改网格规则时至少截一次 390px。
- 截图检查与功能验证共同形成结论。脚本能发现溢出、对比度或崩溃，不能证明界面好看；审计全绿和历史“已验收”都不能替代当次视觉判断。

### 实现与测试如何演进

当前 `.page-shell`、`.stage-grid`、导航与阅读器位置属于样式实现。重新设计时可替换这些约定，同时处理容器嵌套的内边距、flex 收缩、浮层层叠上下文和 Tailwind 样式生成等实际问题。

组件测试中的区块位置、E2E 中的列数和布局审计中的跨页左缘一致，属于相应方案的回归基线。采用新设计时，同步更新布局断言和审计适用范围，保留相册可打开、模式可切换、数据正确、键盘可用等行为验证，在提交说明中解释变化；不能只跳过失败或删除验证来制造通过结果。

## 工作台模式与内容属性

媒体目录有两种内容属性，它们是两种产品，不是同一套交互换皮：

| | 照片目录 | 漫画目录 |
| --- | --- | --- |
| 入口 | 点击相册直接进入照片墙 | 点击相册直接进入阅读器 |
| 主画面 | 按真实宽高比自适应排布的平铺网格 | 单张图片适应屏幕 |
| 交互 | 点开大图、缩放、拖动、全屏、上一张 / 下一张 | 翻页、连续滚动、双页、RTL / LTR、缩放、适配 |
| 状态 | 不留进度 | 阅读进度（读到第几页）、已读 / 未读、双页计数 |
| 偏好 | 密度等照片模式偏好 | 阅读模式、适配方式、翻页方向等阅读器偏好 |

属性只由所属媒体根决定，互斥且只能选一个；目录下的相册与集合一并继承，不按图片数量推断，也没有单本相册的归类动作。两类的偏好与导航互不污染：偏好分存在不同的浏览器存储里，进度只有漫画才有，因此照片那边不存在「进度被另一种用途污染」的问题。

照片墙的视觉基调跟随应用主题（它是浏览页），大图预览是暗场浮层（它是沉浸场景）；阅读器整屏暗场，浮层与控件用白色系。两者不共享同一套外壳。

### 全局工作台模式

上面两种内容各自自洽，但它们此前混在同一套列表里：首页、最近、收藏、未读、标签与侧栏是一份混合清单，照片相册与漫画相册的卡片长得一模一样，点开却是两套语境完全不同的画面，漫画词汇（「继续阅读 / 未读 / 读完」）又套在照片上。这就是「不伦不类」的来源。

工作台模式（`appMode`）就是目录的内容属性，取值 `photo` / `comic`，两档互斥，存在服务端偏好里：

| | 照片工作台 | 漫画工作台 |
| --- | --- | --- |
| 侧栏入口 | 照片库 / 最近浏览 / 收藏照片 | 漫画库 / 未读 / 最近阅读 / 收藏漫画 |
| 列表内容 | 只列照片目录的相册 | 只列漫画目录的相册 |
| 首页专区 | 随手看看（照片墙）/ 接着看 | 继续阅读 / 未读 |
| 索引维度 | 按年份（年份卡 → 这一年的照片墙） | 按作品（作品索引） |
| 继续 | 无 | 继续阅读 |
| 未读 | 无 | 未读 |
| 卡片完成态 | 无 | 已读完 |
| 卡片进度 | 无 | 百分比 |
| 封面画幅 | 方形（展陈墙） | 竖版 4:5（书脊） |
| 色调 | 冷 | 暖 |

侧栏品牌区下方是「照片 / 漫画」分段控件，下面只列当前模式自己的入口：照片模式是「照片库 / 最近浏览 / 收藏照片 / 精选照片 / 足迹 / 人物相册 / 智能搜索」，漫画模式是「漫画库 / 未读 / 最近阅读 / 收藏漫画」。两套菜单完全隔离——漫画那边没有「继续浏览」「未浏览」，照片这边也没有「未读」「已读完」。

隔离不止停在菜单上：模式进 URL 路径，两侧各有自己的路由。照片侧是 `/photo`、`/photo/recents`、`/photo/favorites`、`/photo/picks`、`/photo/travels`、`/photo/people`、`/photo/semantic`、`/photo/albums/…`、`/photo/tags/…`，漫画侧是 `/comic`、`/comic/unread`、`/comic/recents`、`/comic/favorites`、`/comic/albums/…`、`/comic/tags/…` 与漫画阅读器 `/comic/read/…`。这样切模式就是一次普通导航，浏览器前进后退能跨模式，深链也能直接分享；相册的链接永远落在它自己所属的那一侧。

切换模式时能一一对应的只有两侧都有的同名页（最近 / 收藏 / 标签）：相册与阅读器只属于一侧，未读只属于漫画侧，因此它们都回落到对侧首页。

没有第三档「全部相册」：不过滤的一档会让两个模式的菜单互相掺入，用户又要重新分辨哪个入口属于哪边。属性由目录决定，工作台一次只面对其中一半，另一种相册在这个工作台里根本不出现。

隔离要彻底到「另一侧的东西连提都不提」。收藏与历史是全局一份数据（相册、集合、智能标签混在一个列表里），但每个工作台只呈现属于自己这一侧的部分，界面上也不出现「另有 N 项属于其它类型」这类提示——那等于把另一侧的存在又提醒了一遍。

由此带出一条必须守住的判定：**「这一侧看不到」不等于「失效」**。只含漫画的标签被收藏后，在照片工作台里查不到它，但它没有失效，清理失效收藏的动作绝不能把它删掉。失效只表示「库里已经没有这个资源」。这条判定错了就是一次真实的数据丢失，所以它有自己的回归用例。

集合继承所属目录的属性，因此同样参与过滤：漫画目录下的集合不会出现在照片工作台里。它的「作品数」恒为全部后代，但集合的所有成员都在同一媒体根（同属性），所以这个计数天然按侧，不需要再拆一份按属性的计数。集合与标签卡片的计数单位也跟着那一侧走：照片侧说「本」，漫画侧说「卷」。

阅读器整屏脱离 AppShell，侧栏不可见，所以阅读器顶部提供一枚工作台 chip：切模式意味着离开阅读器回到外壳。

帮助浮层跟着模式走：全局操作的措辞随工作台变化（照片工作台是「回到照片库 / 最近浏览 / 收藏照片」，漫画工作台是「回到漫画库 / 最近阅读 / 收藏漫画」），只属于一个模式的快捷键（例如未读页的 `U`）在另一个模式下不列出。照片墙额外多一组大图预览的操作。模式切换刻意不占快捷键——常见候选键都被浏览器的开发者工具或打印占用，而顶栏与设置页都是一步可达的控件。

模式切换控件的位置随可用宽度换挡，但始终只有一份：宽屏（≥1024px）它在顶栏左槽，与全局动作同层；窄屏顶栏放不下，它回到侧栏抽屉里（窄屏时侧栏本身就是抽屉）。侧栏因此只负责「本工作台的入口」这一件事。

### 两侧各成一套的首页与视觉

两个工作台不只是菜单不同：首屏给的东西、翻找的维度、卡片的样子都该不同，否则「隔离」只做了一半。

**首屏专区对称而不雷同。** 漫画侧有「继续阅读 / 未读」，因为漫画有阅读进度与已读状态；照片侧没有进度可言，于是给「接着看 / 最近加入 / 随手看看」——上次打开过的那本、按业务日期倒序的最近照片相册，加三本随机的候选（一本主角 + 两本小候选，凑齐面板下半那块地）。两侧各占首页第一屏的同一位置，骨架共用（`home-overview` + `discovery-panel`），面板外壳也共用，但内容与措辞完全分开：漫画的封面是竖版书脊，照片是方形展陈。照片侧的空态推荐位同样按侧给：漫画推未读，照片推最近加入。

**照片侧三块专区的排布。** 宽屏下「接着看」与「随手看看」并排等宽，照片墙移到第二行通栏——横贯一行更像一面展陈墙。没有浏览记录时（照片墙回到宽栏）版式与原来一致；窄屏只有一栏，三块按文档顺序单列排下。

**「那年今日」是照片侧才有的一段。** 它按月日找出往年这一天拍过照的相册，靠的是文件名里推断出来的拍摄时间 —— 没有拍摄时间就没有「那天拍过」这句话，因此它不参与漫画侧。没有命中时整段不出现，不占章节号，也不用空态占位。卡片上写的不是相册的代表日期，而是命中的那一天：相册的 `date` 是它内部日期的众数，与「今天这个月日」未必是同一天。

**这一段摆的是那一天的那一张照片，不是相册的通用封面。** 封面只说明「这本相册里有这一天」，回答不了「往年这天我拍到了什么」；把封面摆在这一段，读者看到的是一批与今天无关的相片。照片的日期证据同样来自文件名推断，服务端给不出这一张时（扫描缓存与文件名不一致等）退回相册封面，并且不假装封面就是那天拍的那张。点照片直接看那一张，看完能从标题回到原相册 —— 这一段是照片，出去的路却是相册。

**「接着看」的边界。** 它是漫画侧「继续阅读」的对称物：侧栏给一枚常驻条目，首页给一块首屏专区。照片相册其实一直在记访问历史，只是原先只有「最近浏览」页在用。照片不留浏览位置，所以「接着看」回到**相册**，回不到**具体某一张**——它的线索只有「上次浏览」这个时间，不画进度条，也不出现「读到第几张」。这条边界写在界面上，也写在实现里：照片侧不读阅读活动，因此没有可显示的页码。

**两侧的词各归各。** 计数单位与动作动词跟着内容属性走，不跟着「当前在哪个工作台」走：照片说「张 / 本 / 浏览」，漫画说「页 / 卷 / 阅读」。漫画侧的一张图就是阅读器里的「一页」，相册卡片与阅读器必须用同一个词；照片侧则从头到尾只说「张 / 本」。两侧共用的组件（悬停预览、搜索结果、集合页标题、属性弹窗）按每张卡自己的 `contentKind` 取词，取不到时按照片兜底。词表集中在 `utils/workbench.ts`，它是唯一真相源。

**类型词也分侧。** 一部作品在漫画侧叫「作品」，在照片侧叫「集合」；一个单本在漫画侧叫「相册」，在照片侧叫「文件夹」。首页视图筛选的那一排 chip（全部 / 类型 / 类型 / 标签）用的就是这两个词 —— 漫画侧是「全部 / 相册 / 作品 / 标签」。卡片副标题、搜索结果、属性弹窗、文档标题都要跟着同一份词表，不然同一个东西在一页之内会出现两种叫法。

**「卷」是漫画侧的计数单位，不是「本」。** 卡片上说「14 卷」，侧栏与未读页就该说「14 卷还没读完」「还有 71 卷没读」；两边混着说，用户会以为是两个不同的数量。

**索引维度跟着内容走。** 照片的天然维度是时间，所以按年份分组；漫画常常不以年份命名，一部作品横跨好几年，按年份分会把同一部作品拆散在好几处，因此漫画侧改按「作品」分组——集合就是作品。年份索引两边都留着，但两个动作分得很清：照片侧年份卡的主操作是**看这一年的照片**（`/photo/years/<年份>`），漫画侧是**进入那一年**（通常是那个同名集合，没有集合时进文件最多的那一本）；卡片右上角的漏斗始终是**只筛这一年**——它筛的是下方网格。漏斗在桌面上随悬停浮出（免得一排年份卡各挂一枚白方块，把索引条的节奏切碎），触屏上没有悬停，因此常驻可见。

**视觉基调一冷一暖。** 差异只落在品牌点缀与 hero 面板底色两处（`--brand*` / `--feature-bg`，按 `:root[data-theme][data-mode]` 组合覆盖），画布、文字、描边保持中性灰阶——外壳无彩，彩色留给内容本身。封面画幅同样分侧：照片侧方形（展陈墙），漫画侧竖版 4:5（书脊）。模式写在 `<html data-mode>` 上，由 URL 路径推导，因此切模式就是一次普通导航，色调随之切换。

## 虚拟列表与媒体网格

相册摘要由 `AlbumGrid` 虚拟化。照片墙的每一行高度由自适应排布算法确定（宽高比来自服务端的像素宽高），`Virtuoso` 只按行虚拟化，不参与测量行高；行内保持服务端媒体顺序，向分页钩子回报时换算为原始媒体序号。

- 排布算法是纯函数（`components/wall/justifiedLayout.ts`）：一行能放下就继续放，放不下换行；每行等比缩放铺满容器宽度；行高夹在目标行高的上下限之间，竖图不会顶满屏幕；末行不满时保持目标行高，不为填满而把一张图撑成巨幅。
- 容器宽度变化（侧栏折叠、窗口缩放）时重排；已渲染的行不会因为后续页到达而跳动——排布是贪心的，后到的条目只会影响它自己所在的行。
- 未知尺寸退回默认比例（3:2），视频按 16:9；服务端给出真实像素宽高后即刻使用。

- 保留服务端总数对应的轻量占位槽（照片墙按默认比例占位），远距离滚动后持续补页，失败保留已加载内容并支持重试，不为整本相册挂载完整媒体 DOM。
- 页面留白与最大宽度放在虚拟列表外层，视口与列表保持同宽；行内间距计入行高，首尾不满一行的条目仍可到达。
- 照片墙使用 `overscan={600}` 和上下各 600px 的视口余量。`increaseViewportBy` 不能贪心：数值过大时 `Virtuoso` 的尺寸树会在一次测量里展开过深，触发「Maximum call stack size exceeded」，整页被错误边界接管。单元测试对这三个参数设了上限断言。阅读器连续模式使用独立参数。
- 修改虚拟化、窗口或容器后，检查拖到底部、返回顶部、远距离跳转、分页失败重试、断点与密度切换；运行 `audit:crash` 时固定相册、访问次数、视口和缩略图来源。单次打开或有限样本零崩溃不能证明所有场景都无异常。

## 验证方法

按影响范围验证：局部修改检查受影响组件、页面与断点，全局视觉系统或导航重做则复查首页、最近、收藏、未读、设置、相册、标签与阅读器。以 390 / 768 / 1024 / 1440 / 1920 宽度、明暗主题与网格/列表为起点，补查新方案的临界断点、短屏和数据状态，不固定各档版式。运行对应组件测试和 E2E，布局/对比度审计作为检查工具；涉及虚拟网格再跑崩溃探针。截图放 `frontend/.smoke/<任务>/`，不入仓。

在 `frontend/` 下运行，默认连接已启动的 `http://127.0.0.1:5173`；需要 Playwright Chromium（首次执行 `npx playwright install chromium`）：

```sh
npm run audit:layout
npm run audit:contrast
npm run audit:contrast -- --self-test
npm run audit:crash
npm run shot -- --out .smoke/review
```

整页截图看不清某一处时，用元素截图单独拍一块（`--route` 是要打开的路由，`--sel` 是 CSS 选择器）：

```sh
npm run shot:el -- --route /comic --sel ".hero-panel__feature" --out .smoke/hero
```

应用的内容区是内层滚动容器，整页截图（`LG_FULL=1`）拍不到下半屏。要看
下半屏的东西，用滚动截图：它把内容区滚到指定位置后拍视口。

```sh
node scripts/shot-scroll.mjs --route /photo/travels --scroll 900 --out .smoke/travels.png
```

也可在仓库根目录使用独立临时媒体库，脚本构建并启动服务，E2E 后追加审计或探针：

```sh
cd frontend
npm run test:e2e -- --audit
npm run test:e2e -- --crash
```

页面体积用体积审计量：静态载荷（HTML + JS + CSS 的实际传输字节）、媒体字节、
请求数与 FCP/LCP。

```sh
npm run audit:size                                   # 对着运行中的服务量
npm run audit:size -- --dist                         # 只量构建产物首屏，CI 用这条
```

`--dist` 读 `dist/index.html` 引用的入口 chunk、modulepreload 与样式表，
求和后与预算比较。它不依赖运行中的服务与媒体库，结果确定，适合当 CI 的
守门线；运行时的量要对着生产构建看 —— 开发服务器送的是未打包的模块，
数字没有可比性（脚本会认出开发服务器并跳过预算判定）。

| 环境变量               | 使用范围与含义                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| `LG_BASE`              | 所有审计和截图；目标服务地址                                                                          |
| `LG_PAGES`             | 布局、对比度与截图；逗号分隔路由。仅布局/对比度支持 `album`、`reader`、`tag` 伪路由，截图需要实际 URL |
| `LG_THEMES`            | 布局、对比度与截图；默认 `light,dark`                                                                 |
| `LG_VIEWPORTS`         | 布局与截图；如 `390x844,1440x900`。对比度脚本固定 1440×900，不读取此变量                              |
| `LG_VIEWMODE`          | 布局与对比度；`grid` 或 `list`                                                                        |
| `LG_FULL`              | 截图；`1` 表示整页                                                                                    |
| `LG_CRASH_VISITS`      | 崩溃探针；访问次数，默认 10                                                                           |
| `LG_CRASH_ALBUM`       | 崩溃探针；指定相册名，默认选媒体最多的相册                                                            |
| `LG_CRASH_VIEWPORT`    | 崩溃探针；默认 `1280x720`                                                                             |
| `LG_CRASH_MOCK_THUMBS` | 崩溃探针；`1` 使用假缩略图，默认真实缩略图                                                            |
| `LG_W` / `LG_H`        | 元素截图；视口宽高，默认 1440×900                                                                    |
| `LG_SCALE`             | 元素截图；像素倍率，默认 2                                                                          |
| `LG_STATE`             | 元素截图；追加到 `local-gallery-ui` 的偏好片段，如 `{"viewMode":"list"}`                             |

环境变量只控制验证工具，不覆盖应用 YAML 配置。例如：`LG_VIEWMODE=list npm run audit:layout`。

截图工具默认只拍首页、最近、收藏和未读，且不包含 1024 断点；完整复核应显式设置页面与断点。标签审计优先真实标签；E2E 的临时库包含中文、空格、`+`、`%` 等真实标签。阅读器审计应按相册 ID 直接进入。

### 页面体积基线

生产构建、1440×900、首页实测（2026-11-11）：

| 指标       | 值                                    |
| ---------- | ------------------------------------- |
| 静态载荷   | 114.8 KB（预算 120 KB）               |
| 媒体字节   | 880.1 KB（随库大小与档位变化，只作参考） |
| 请求数     | 71                                    |
| FCP / LCP  | 184ms / 920ms                         |
| 构建产物首屏 | 370.1 KB（预算 420 KB，未压缩）       |

首页首屏改成照片墙之后，媒体字节与 LCP 都上去了：首屏最大的那块内容
从相册封面变成照片本身，缩略图更大、更多。静态载荷涨的是照片墙那几块
chunk（照片条、照片流 hook），仍在预算内；构建产物首屏基本没变。

「构建产物首屏」是 CI 里的守门线：入口 chunk + modulepreload + 样式表
就是首屏要下的全部静态资源，加新依赖或新 chunk 时这条线会先响。
媒体字节不进预算 —— 它随库里有多少张照片变化，守不住也没意义。

大图预览按图片在舞台里的真实显示宽取档，不按视口宽。一张 3456 见方的
照片在 1440×788 的舞台里只显示 788 像素宽，1 倍屏取 1280 档（215 KB），
2 倍屏取 1920 档（464 KB）；按视口宽取则一路顶到 4096 档，服务端对更窄
的源图原样返回原图，一张 3.7MB 的原图就为了看一屏被整个拉下来。

### 审计工具自身的验证

- 布局审计输出溢出、字号、命中区与有效内容宽；当前还将跨页内容左缘一致作为失败条件，阅读器除外；照片墙以含返回按钮的 `.album-bar` 容器边界作为对齐基准，不能把按钮后的文字左缘误当页面留白。这是现有容器方案的检查，采用不同页面布局时需同步更新适用范围，不能直接作为新设计的统一要求。页面崩溃单独报错，不能算作空页面通过。
- 对比度使用文字 DOM、图片上文字像素、图标像素三条通道。背板按几何交叠与绘制顺序确定，不能只查祖先链；`elementsFromPoint` 会漏掉 `pointer-events:none` 蒙版。
- 像素包围盒须完全位于截图内，取样不越过背板；自身底色取中位数附近的簇，周边取贴字的四条直边，排除抗锯齿过渡带与圆角切角，避免药丸角标假阳性。
- 每增加判定路径都补已知好坏样本并运行 `--self-test`（布局审计覆盖普通列表、照片墙返回按钮与故意偏移的反例），不能通过放松标准、删断言或跳过失败页面制造通过结果。
