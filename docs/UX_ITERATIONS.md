## R0 · 基线重建（2026-11-03）

### 背景

上一轮（见 [UI_REDESIGN.md](./UI_REDESIGN.md)）把界面从"后台"往"画廊"拉了一大截，
`docs/UI_ACCEPTANCE.md` 里 A1–A7、B1–B8 全绿。**但历史验收通过 ≠ 当前设计优秀**：
本轮重新建立视觉质量基线，不受此前 VERIFIED 状态约束。

### 观察（真实运行 + 截图）

- 环境：Go 后端 `:8080`（真实媒体库 104 相册 / 28 集合）+ Vite `:5173`，
  Playwright Chromium，**DPR=1、浏览器缩放 100%**（先验证，排除"截图误判"的可能）。
- 基线截图 32 张：`frontend/.smoke/base0/`（明暗 × 390/768/1440/1920 × 4 页）。
- 量化基线：`npm run audit:layout`（本轮新增脚本）。

### 批评

**专业设计师视角**

1. 首页没有主角。"图像库"这个导航性词汇以 30px 占据视线最重的位置，而真正的主角
   （在读的那本书的封面）只有 140×176，被塞进一个 1340×200 的灰色横幅里，
   右侧 1000px 是空的。
2. 层级倒置：30px（页面框架）> 15px（区块标题）> 13px（卡片标题）。
   **界面比内容大**，这正是"像后台"的技术成因。
3. 版面是"等分网格堆叠"：未读 6 张 + 在读 5 张，同尺寸同密度连成一片 11 张卡的墙，
   没有任何主次节奏。
4. 视频封面是灰底空框 + "▶ —"，是全页最像"文件损坏"的地方。

**普通用户视角**

1. 打开应用，标题写着"图像库 / 104 本相册 / 28 个集合" —— 像磁盘清理工具的统计页。
2. "接着读上一本"确实在第一屏，但那条横幅长得像加载失败的空面板。
3. 搜索框缩在左上角，右边一大片空顶栏，不知道该点什么。
4. 有 3 张卡是灰的，以为文件坏了。

### 量化结论

| 指标 | 实测 | 判定 |
|------|------|------|
| 1920px 主内容占视口 | 75%（1440/1920），左右各 240px 死白 | **A 成立** |
| 1440px 主内容 | 85.6%（受 208px 侧栏挤压，无额外死白） | A 在超宽屏才成立 |
| 主导文本字号 | 12.5px × 95 处（首页可见文本的最大宗） | **B 成立**（不是浏览器缩放问题） |
| 最低字号 | 10.5px（kbd）、11.5px（badge / 状态字） | B 集中在"主内容是 meta"而非"全部都小" |
| 控件高度 < 28px | 首页 18 处（含 6 个 24px 的年份筛选按钮） | B 的可操作面证据 |
| 横向溢出 | 0（5 档 × 明暗 × 4 页全绿） | 无回归风险 |
| DPR / 缩放 | 1 / 100% | 已排除"截图缩放误判"这一根因 |

**A、B、C、D、E、F 六条假设全部成立**，但根因各不相同：
A 是容器上限；B 是字号分配（主内容被当成 meta 处理）；C 是构图（横幅而非封面墙）；
D 是信息架构（框架 > 内容）；E 是封面策略单一；F 是层级倒置。

### 构思（本轮方向）

针对首页提出两个有实质差异的方案：

**方案 A ——「编辑式封面台」**：
继续阅读不再是横幅，而是**一张大海报 + 右侧信息栏**：封面放大到 ~320×400，
标题与 CTA 紧贴封面右侧，整体宽度自适应（约 760px），其余在读书目降级为右侧小海报列。
信息结构：主角 → 次要 → 其它。
优点：改动局部、聚焦、CTA 距离最短；缺点：仍是一个"卡片"，横向仍留一段空白。

**方案 B ——「胶片带 / 封面墙」**：
继续阅读改为一整条**海报带**（filmstrip）：所有在读相册按统一高度（200–260px）横排，
**宽度按各自长宽比自适应**，第一本更高（280px）形成主次。下方未读区同理，
但高度更矮（160px）。时间线降为"年份筛选带"。
优点：内容成为主角、长宽比问题自然解决、横向空间被真正用满、有辨识度；
缺点：需要拿到封面原始宽高比（后端是否提供？需确认）；横向溢出/窄屏需要额外处理。

→ **决定：Cycle 1 采用方案 B 的核心（封面带），但保留方案 A 的"主角更大"原则。**
先确认后端是否能提供封面宽高比。

## R1 · 首页封面台与视觉基线重设（2026-11-03）

### 假设

1. 首页不需要"横幅"这种形态。横幅天然要求内容横向铺满，而信息量不足以铺满，
   于是必然出现空洞。把主角从"横幅"换成"一张大封面"，空洞自然消失。
2. 内容没有存在感，一半来自**比例错配**：主封面比它自己的次级卡还小。
   把主封面放大到货架海报的 1.6 倍以上，层级会立刻清晰。
3. 容器上限与标题层级是可量化的硬伤，改掉即可，不需要靠"感觉"。

### 备选方案（比较）

| 方案 | 结构 | 取舍 | 结论 |
|------|------|------|------|
| A「编辑式封面台」 | 一张大封面 + 紧贴其右的信息栏 + 其余在读降级为小海报列 | 改动局部、CTA 距离最短；但右栏仍有留白 | **采用（与 B 合并）** |
| B「胶片带 / 封面墙」 | 所有在读按统一高度横排、宽度按各自真实比例自适应 | 封面比例问题解决得最彻底；但需要后端提供封面宽高比 | **部分采用**：后端目前不提供宽高比，改用"按媒体类型定比例"（图片 2:3 / 视频 16/9），避免为了排版去改后端契约 |
| C「左轨 + 沉浸封面墙」 | 左侧 300px 固定"在读轨"，右侧封面墙铺满 | 接近独立评审推荐的方案 B；能彻底利用宽度 | 下一轮候选：需要处理双滚动区与"最近"页语义重叠 |

### 实施（提交 `8ec71ce`）

- 继续阅读 → **封面台**：300×450 的 2:3 主封面（走 `/api/previews` 640px，
  避免放大 320px 缩略图）+ 墙签式标题 + 紧贴封面的进度读数 / 进度条 / 主操作
  + 其余在读的横向货架。
- 未读 → **横向封面货架**（图片 2:3、视频 16:9），右端渐隐提示还有更多。
- `.page-shell` 上限 1440 → 1600，padding 改 `clamp(16px, 2vw, 40px)`；
  新增 `.hero-title`（26px）、`.section-title` 15 → 17px、`.btn-sm` 30 → 32px。
- 顶栏图标组贴到视口右缘；顶栏内层复用 `.page-shell`，与正文共用左基线。
- 网格列数由固定 6 列改为 `auto-fill minmax(164px, 1fr)`。
- 视频封面 letterbox 底色改用新令牌 `--bg-media`（恒深色）。

### 验证

| 项 | 前 | 后 |
|----|----|----|
| 1920px 主内容宽度 | 1440px（视口 75%，主区 84%） | **1600px（视口 83.3%，主区 93.5%）** |
| 主封面尺寸 | 140×176（比次级卡还小） | **300×450（货架海报的 1.67 倍）** |
| CTA 与封面的视觉距离 | ~1000px | **~60px**（同在左栏） |
| 控件 < 28px | 18 处 | **2 处** |
| 横向溢出 | 0 | 0 |
| 对比度 AA | 全绿 | 全绿 |
| 单测 / Lint / Build | 582 绿 / 0 error / 通过 | 同 |

截图：`.smoke/base0/`（前）→ `.smoke/r1c/`（后），明暗 × 4 断点共 32 张。

### 前后差异（逐张看图得到的具体事实）

- **light-1920-home**：旧版首屏是一块横贯 1340px 的浅灰盒子，右侧约 1000px 只有
  一颗按钮和一颗 ×；新版首屏左侧是一张 300×450 的清晰封面（图片走预览接口，
  不再是放大的缩略图），右侧信息与封面同屏，主按钮紧贴标题。
  旧的"顶栏图标停在 x=850、右侧空 1000px"变成图标贴到 x=1900。
- **light-1440-home**：旧版主封面只有货架海报的一半大；新版主封面 1.67 倍于
  货架海报，"继续阅读 / 其余在读"的主次一眼可分。
- **dark-1440-home**：旧版横幅在深色下是一整块纯黑空洞；新版深色下封面与
  背景分离清晰，货架右端渐隐提示"还有更多"。
- **未读区**：旧版 6 张卡里 3 张是灰底空框（视频 letterbox 落在浅灰底）；
  新版视频卡是深色画布 + 圆形播放徽标 + "正在加载…"，有明确的图形语言。

### 踩过的坑（写下来防止重蹈）

1. **Tailwind 工具类名**：令牌叫 `--bg-media`，而颜色键是 `bg-media`，
   工具类因此是 `bg-bg-media` 而不是 `bg-media`。写错时**样式表里根本不存在这条规则**
   （computed background 直接是 transparent），不报错、只是没效果 ——
   排查时先在浏览器里查 `document.styleSheets` 里有没有这条规则，别急着怀疑 HMR。
2. **新增 Tailwind 颜色需要重启 dev server**：`tailwind.config.ts` 改动后
   已运行的 Vite 进程不会重新生成工具类。改完配置要重启前端。
3. **`networkidle` 在这个应用里不可用**：页面含 SSE 长连接，且 `/api/previews`
   首次生成预览图可能耗时数秒。截图 / 审计脚本改用
   `domcontentloaded` + 等待 `document.images` 解码完成。
4. **主封面用缩略图会糊**：`/api/thumbs` 走 `imaging.Fit(320, 350)`，
   最大边只有 320px。300px 宽的主封面必须走 `/api/previews?w=640`。

### 下一轮重点

- 侧栏中段大片空白（B8）、"随机一本 / 随机未读"与首页按钮重复；
- 顶栏搜索权重仍偏低（B7）；
- 「最近 / 收藏 / 未读」三页与首页同构，缺少语义差异（B13）；
- 未读货架右侧仍有约 375px 空档，需要决定"留白"还是"补内容"。

## R2 · 导航、封面台收口与页面一致性（2026-11-03）

### 假设

1. 侧栏中段的空白不是"侧栏太窄"，而是**没有一个值得放在那里的东西**。
   与其把导航摊开，不如把全局最高频的动作（接着读）钉在侧栏底部。
2. 首页之外的几页之所以"像后台"，是因为它们都只是**同一张卡片的网格**，
   而视频相册页干脆是**一套独立的写死样式**（另一套标题字号、另一套按钮）。
3. 不同宽高比的媒体要真正区分，区别点不在"裁切方式"，而在**给它们各自的画幅**。

### 备选方案（比较）

| 问题 | 方案 A | 方案 B | 结论 |
|------|--------|--------|------|
| 侧栏空白 | 收窄侧栏到 176px | 底部加「接着读」迷你卡 | **采用 B**：空白不是尺寸问题，是内容问题；且"接着读"是全局最高频动作 |
| 视频画幅 | 4:5 格里 `object-contain` | 视频单独用 16:9 画幅 | **采用 B**：竖框框宽银幕必然留边，留边是噪音 |
| 页网格取景 | `object-contain` 整页显示 | `object-cover` + 偏上取景 | **采用 B（并撤销先做的 A）**：整页显示让横构图照片在竖格里留下大片上下灰边，整页网格变成一堆灰框；实测后回退 |
| 视频相册页标题 | 保留 28px 独立样式 | 复用 `.page-title` / `.btn` | **采用 B**：同一应用两套标题字号会让"标准"不可预期 |

### 实施（提交 `3562f64`）

- **侧栏**：底部新增「接着读」迷你卡（封面缩略图 + 标题 + 进度条 + 页码），
  数据来自与首页同一个 dashboard 查询（React Query 共享缓存，不额外请求）；
  移除与「未读」页 / 首页重复的「随机未读」按钮。
- **跳转逻辑抽公共函数** `utils/continueReading.ts`（首页封面台与侧栏迷你卡共用），
  避免两处生成不同的 URL。
- **首页页标题让位**：新增 `.page-title--compact`（24px），首页标题不再是全页最大字号，
  主角标题 `.hero-title`（26px）成为最大的字。
- **视频角标**：时长未知时不再显示 "—"（破折号看起来像"读不出来 / 坏了"），只留播放图标。
- **封面取景**：相册封面统一偏上取景（`object-position: 50% 25%`），漫画封面的标题与
  人物头部不再被裁掉。
- **媒体画幅**：纯视频网格改 16:9 + 深色媒体画布；混合网格里视频格用深色画布；
  视频相册页的大封面同样用深色画布。
- **视频相册页 hero**：标题改用 `.page-title`，按钮改用 `.btn` 系列，
  CTA 从标题下方移到同一行的右端（原位置让整行右侧空掉一大片）。
- **货架容量**：继续阅读的货架从 5 本扩到 10 本（宽屏上 6 本只占半行，右侧像"排版没做完"）。

### 踩过的坑

1. **`object-contain` 的代价**：整页显示看起来"更忠实"，但横构图照片在 3:4 竖格里

   → 教训：新增"卡片套在非默认底色上"的组件时，先想一遍底色组合。

## R3 · 页面语义差异、密度分级与收尾核对（2026-11-03）

### 假设

1. 「最近 / 未读 / 收藏 / 全部图像」看起来一样，是因为它们**只有标题不同**，
   下面都是同一张 4:5 的密集网格。语义差异应该体现在**画幅与密度**上：
   收藏是"精选陈列"，未读是"待办清单"，全部图像是"浏览"。
2. 卡片 meta 行 12.5px 是"内容存在感不足"的最后一块：首页可见文本里
   12.5px 曾占 95 处（绝对多数）。
3. 剩下两条被记为"问题"的条目，可能根本不是问题 —— 需要实测而不是推测。

### 实施（提交见下）

- **AlbumGrid 新增 `coverRatio` / `cardMinWidth`**：收藏页改为 2:3 海报比例 +
  224px 疏朗网格（精选陈列），未读 / 最近 / 全部图像保持 4:5 + 164px 密集网格
  （清单与浏览）。这是三页之间第一次有**结构性**而非标题性的区别。
- **卡片 meta 行 12.5px → 13px**：首页 12.5px 文本从 95 处降到 62 处，
  13px 从 18 处升到 45 处。
- **实测核对两条疑似问题**：
  - B12「状态栏切边」→ **不是问题**。实测 `main` 的下边界与状态栏上边界同为 868px
    （两者是 flex 兄弟，不存在覆盖），滚到底后最后一行完整可见。
    截图 `.smoke/r3/recents-bottom.png`。
  - B14「阅读器顶栏在亮图上不可读」→ **不是问题**。顶栏已带 `.scrim-top`
    （黑色 88% 覆盖到 62% 高度），实测 computed backgroundImage 生效，

### 踩过的坑

1. **新增小字会拉低可读性基线**：侧栏紧凑行一开始用 11.5px，审计立刻报出

2. **Tailwind 任意值不能写成模板字符串**（上一轮已踩过一次）：

4. **1×1 透明 PNG 放大后是纯黑块**：临时素材用 canvas 画真实颜色与横竖比例，

## R5 · 舞台封洞、浮层对比度与列表视图收口（2026-11-03）

### 假设

R4 留下的四条待办里，前三条其实是同一类问题：**内容没有站在该站的位置上**。

1. 舞台右上角那块空洞不是"留白不够优雅"，是**违反北极星**：
   §1 写着「任何一屏里，图像的视觉重量必须大于界面框架；禁止出现
   "大面积留白 + 小图 + 文字"的版面」。1920 下右栏宽 1244、信息栏只占 520，
   等于这一栏有 58% 是空白 —— 空白夹在内容之间会被读成"排版没做完"，
   只有夹在导航与内容之间才算留白（§4.4）。
   假设：**右栏不该由文字占位，该由图像占位**。
2. 收藏页空态的空白不是"收藏为空时本就如此"这么无害 —— 它同时是一条
   教学路径。文案在教用户「点封面右上角的星标」，而星标在桌面端默认
   hover 才露出。**指着看不见的东西等于没说**。
3. 阅读器底栏在纯白图片上的可读性不是"应该没问题"，而是**没被查过**：
   对比度审计只跑静态路由，阅读器的浮层（顶栏 / 底栏 / 药丸工具条）
   全部是压在图片上的白字，静态算不出背景，只能靠像素判定那一遍。
4. 列表视图"没按新基线复核"的具体落点：R2 把网格卡的 meta 行提到 13px，

### 踩过的坑

1. **Tailwind 只认 5% 的整数倍渐变色标**：`from-78%` 会被静默丢弃 ——
   不报错、样式整条不生成，渐变退回默认起点。实测 `from-55%` 有效、
   `from-78%` 与 `from-[78%]` 都无效。写不透明段时只能取 5 的倍数。
2. **对比度采样要量"文字外一圈"，不是文字本身**：第一次把渐变改成
   `from-80%` 反而从 3.64:1 掉到 3.07:1 —— 因为文字包围盒外一圈
   采到的是渐变最淡的那一段。压图片的文字必须让**不透明段盖住整行文字**，
   而不是让渐变"看起来更黑"。
3. **截图脚本里的图片等待会假通过**：1440 断点第一次拍到主封面是空白，
   不是 bug，是 262 页相册的 640px 预览还没生成完，等待超时后仍然截了图。
   复核前先重拍一次再下结论。
4. **`page.route` 转发到临时后端时必须带上 `method` / `headers` / `postData`**：
   只传 url + 部分 headers 会把 POST 请求体丢掉（上一轮已踩，本轮沿用）。
5. **flex 行的每个子元素都要有宽度约束**：右栏里的替补内容（未读区，
   根元素是 `.page-shell`，`width:100%`）作为 flex 行的直接子元素时，
   会按自身宽度撑开并把整行顶出容器 —— e2e 实测 1440 下主内容横向
   溢出 203px。裹一层 `flex-1 min-w-0` 才老实。
   **教训**：改版面后必须重跑 e2e 的横向溢出用例；它比肉眼更容易抓到
   "这一行比容器宽"的问题。

## R6 · 次级页面审计：触控目标、层级倒置与两个真实缺陷（2026-11-03）

### 假设

R0–R5 的审计对象一直是首页与其周边（侧栏 / 顶栏 / 收藏 / 未读 / 时间线 /
阅读器浮层）。**相册详情页与设置页从未被量过** —— 而它们恰好是全站
最容易出问题、又最没人看的地方。本轮把审计范围扩到它们，并假设：

1. **设置页是全站最差的一页**：它的表单控件密度最高、字号最杂，很可能
   是触控目标与字号缺口最集中的地方。
2. **相册详情页的 hero 封面偏小**：桌面端 120×152，比它下面网格里的缩略图
   （标准档 ~190×235）还小 —— 一页里"代表这本"的那张图成了整页最小的图。
3. **顶栏下拉（搜索结果 / 更多菜单）可能被正文盖住**：顶栏带 backdrop-blur，
   自成一个层叠上下文，面板里的 z-index 只在顶栏内部有效。

### 备选方案（相册 hero 封面尺寸）

| 方案 | 做法 | 结论 |
|------|------|------|
| A 保持 120×152 | 不动 | 页面上"代表这本"的图比内容缩略图还小，层级倒置 |
| B 放大到 200×267 | 2:3 海报，与首页封面台同量级 | **选中**，但先要确认虚拟网格扛得住 |
| C 放大到 160×213 | 折中 | 只比 A 大 40%，层级问题没真解决 |

### 实施（提交 `6be6359` / `fe9648f` / `b3801bb` / `6149b49`）

- **设置页与全站的触控目标**（`src/routes/Settings.tsx`、
  `ServerConfigPanel.tsx`、`GlobalSearch.tsx`、`ListFilterBar.tsx`）
  - 开关：视觉仍是 20px 药丸，外层按钮撑到 28px（药丸居中）——
    **视觉尺寸与命中区可以分开**，这是这轮最有用的一条。
  - 缓存徽标里的"清空"按钮 16×16 → 28×28（图标仍 9px）；
    徽标标签与"重启""LOCAL"等小字 11.5px → 12.5px。
  - 全局搜索输入框撑满 40px 胶囊（此前只有内容高度 23px —— 全站最高频的
    控件反而是全站最小的命中区）。
  - "最少图数"输入框 20.6px → 28px。
- **相册详情页 hero**（`src/routes/Album.tsx`）
  - 图片相册封面 120×152 → 200×267；视频相册 160×224 → 200×300
    （两个 hero 一样大，不因媒体类型缩水）。窄屏仍是 104×132。
  - 缩略图角标 11.5px → 12.5px（该页此前是全站 <12.5px 文本最多的一页）。
- **顶栏层级**（`src/components/layout/Toolbar.tsx`）

- **审计脚本覆盖**（两个 audit 脚本）

### 前后差异（逐张看图得到的具体事实）

- 相册详情页（1440，明暗各一张）：封面从 120×152 变成 200×267 后，
  封面成了页内最大的图，标题与元信息贴在它右侧；网格的第一行仍完整可见。
- 设置页（1440）：开关的命中区变大但外观一字未改；缓存徽标里的垃圾桶
  图标仍是 9px，只是周围多了一圈可点的范围。
- 顶栏搜索（1440，明暗各一张）：结果面板完整浮在正文之上，
  明暗两套主题都确认过。
- 相册网格（1280×720）：滚到底部后最后一行是真实图片，不是灰色占位块。

### 踩过的坑

1. **视觉尺寸 ≠ 命中区**：开关 20px 高不代表只有 20px 能点。把外层按钮
   撑到 28px、内层药丸居中，视觉一字未改而命中区达标 —— 触控目标的问题
   不一定要靠放大视觉尺寸解决。
2. **`itemSize` 对 VirtuosoGrid 无效**：想让它把 CSS grid 的行间距算进
   条目高度，实测 0 次调用（那是 Virtuoso 列表的 prop）。把行间距挪进
   格子（gap-y-0 + 格子内 pb）也不管用：估算值纹丝不动。
   真正管用的是 `increaseViewportBy` —— 多渲染一截窗口，估算误差被覆盖。
3. **虚拟网格的估算误差 ≈ 两行**：不是按条目数线性增长的，所以一个固定
   的窗口余量（1600px ≈ 6 行）就能覆盖它。
4. **e2e 抓到的是"被 hero 放大暴露出来的老缺陷"**：错误码不是分页逻辑，
   而是渲染窗口；没有那两条 e2e 用例，这个缺陷会一直藏着。

### 本轮之后仍未解决（下一轮待办）

- 首页「未读」货架与「其余在读」分属两种结构（横向货架 vs 封面网格）。
  本轮复核的结论是**两者语义不同、刻意区分**（货架=推荐位、封面墙=清点），
  且 1920 下尺寸分档（240 vs 190）进一步强化了层级，不做统一；
  1440 下两者尺寸接近，但区块标题与结构仍能区分。下轮若要动，先定语义。
- 列表视图在 1440（内容宽 1232）仍是单列，标题与右侧计数之间相距
  ~700px；超宽屏（≥1536）才切双列。1280 单列 / 1920 双列这条规则由
  e2e 用例锁定，改动要先改用例。
- 收藏页的失效收藏提示仍靠一条文案说明"收藏记录的是路径标识"，
  对新用户偏技术。
- 设置页在 1440 下内容列只有约 700px，右侧整片空 —— 表单页的窄列是
  常见做法，但和全站 1600px 的内容宽度并置时略显不齐，未动。

## R7 · 阅读器暗场与首屏裁切：看不见的箭头、白板浮层、被裁掉的主操作（2026-11-03）

### 假设

R0–R6 的审计对象一直是"页面"（首页 / 相册详情 / 设置 / 列表页）。**阅读器
是整个应用停留时间最长的一屏，却从没被量过版式** —— 它只在 R5 被查过
对比度。本轮把阅读器纳入审计，并假设三件事：

1. **阅读器里的浮层没跟上暗场约定**：画布恒为深色（`bg-neutral-950`），
   但「更多」菜单、快捷键帮助、toast 都沿用应用主题的浅色卡片
   —— 这正是信息面板注释里自己写下的"黑底阅读器里嵌一块白板"。
2. **画面左侧的跨卷导航箭头在亮图上等于没有**：白图标直接压照片，
   亮图上几乎看不见；而且**对比度审计根本查不到图标** —— SVG 没有
   文字节点，审计只遍历文本节点。
3. **首页舞台是照着 1920×1080 定尺寸的**：在 1440×900 这类最常见的
   笔记本高度上，「继续阅读」主操作会被滚动容器裁掉。

### 备选方案（阅读器浮层配色）

| 方案 | 做法 | 结论 |
|------|------|------|
| A 保持浅色卡片 | 浮层继续跟应用主题 | **否**：黑底里嵌一块白板；且信息面板已经是暗的、菜单又是浅的，两块浮层自相矛盾 |
| B 阅读器内浮层统一深色 | `Popover` / `ContextMenu` / `HelpOverlay` / `Toast` 加 `tone="reader"` | **选中** |
| C 深色毛玻璃 | 全部换成 `neutral-900/80 + backdrop-blur` | 备选：与底部工具条一致，但纸面质感丢失，且焦点环在石墨强调色下仍然不可见 |

### 备选方案（舞台高度怎么缩）

| 方案 | 做法 | 结论 |
|------|------|------|
| A 媒体查询分档 | `max-height: 920px → 300px` 之类 | **否**：分档在断点附近会"差 1px 就放不下"——实测 1440×900 用 320px 时正好超出 1px，翻到下一档又突然小一截 |
| B 连续函数 | `--stage-cover-w: clamp(240px, calc(100dvh - 440px), 480px)` | **选中**：可用高度是视口高的线性函数，任何高度都留同样的余量 |
| C 整块舞台等比缩放 | 舞台整体缩，连右栏一起 | **否**：右栏不填满 → 右侧又出现空洞（R5 刚封掉的那个洞） |

### 实施

**A. 阅读器暗场**

- `Popover` / `ContextMenu` / `HelpOverlay` 加 `tone`（`theme` 默认 / `reader`）：
  容器 `bg-neutral-900/95 + border-white/15`，菜单项 `text-white/80`，
  分隔线 `bg-white/12`，分组标题 `text-white/50`。
- `HelpOverlay` 用 `data-tone="reader"` 标记，配套一条**不分层**的 CSS：
  `[data-tone="reader"] :focus-visible { outline-color: rgba(255,255,255,.85) }` ——
  浅色主题的强调色恰好是近黑的石墨色，不改的话焦点环是"黑底上的黑框"，
  等于没有焦点指示（未分层才压得过 Tailwind 的 `outline-none`）。
- `Toast` 按路由判断：`/gallery` 下走深色。
- 快捷键浮层底部加渐隐 mask，列表不再把最后一行切一半。

**B. 看不见的图标**

- 跨卷导航箭头加恒定深色圆底（`bg-neutral-900/55 + ring-white/10`）：
  箭头还是白色，但局部背景永远是深色 → 对比度不再取决于照片内容。
- 设置页强调色选择器的对勾 `text-fg` → `text-white`（石墨色块上是黑对勾，
  等于看不见）。
- `.kbd` / `.kbd-light` 10.5px → 12.5px：键帽是全站最后一个 <12.5px 的例外。

**C. 图标对比度审计通道（本轮的工具改动）**

- `contrast-audit.mjs` 新增第三条通道：遍历可见 `svg`，取计算后的
  `color` 作为前景，按包围盒外一圈像素算底色，阈值 **3:1**
  （WCAG 1.4.11 非文本内容）。
- 给这条通道配了自检样本（白图标压白底 / 压黑底），**坏样本必须被判不合格、
  好样本必须被判合格**，否则工具报"全绿"没有意义。
- `layout-audit.mjs` 新增 `reader` 伪路由；两个脚本的默认页面清单都补上
  `reader`。
- `contrast-audit.mjs` 的 `openReader` 改成直接构造 `/gallery?path=…`：
  原来靠"点开始浏览"进阅读器，而视频相册的按钮是「开始播放」→ 静默跳过，
  量到的其实是相册页。

**D. 首页舞台按视口高度收缩**

- `--stage-cover-h: clamp(240px, calc(100dvh - 440px), var(--stage-cover-max))`
  （`--stage-cover-max` 在 ≥1536px 时是 528px，否则 480px）。
- **左栏宽度固定（320/352px），只让封面在栏内收窄**：缩左栏会让右栏变宽、
  次级封面变大，主角/次级的比例从 1.68 掉到 1.24。
- 墙签（标题 + 进度 + 主操作）宽度跟随封面，短屏收窄时仍与封面左右对齐。
- 短屏（1280~1799px 宽且 ≤880px 高）时右栏网格改 **5 列 + 10 条**
  （`.stage-grid`），把比例拉回 1.58。
- 首页页头上下留白 `pt-9 pb-6` → `pt-6 pb-5`（−16px）。

**E. 顺手修掉 R6 留下的爆栈**

- R6 为"末行能渲染"把 `increaseViewportBy.bottom` 提到 1600px，
  结果 405 个视频的相册一进页面就抛 `Maximum call stack size exceeded`
  （Virtuoso 内部尺寸树是递归展开的，测量条目太多直接爆栈），整页被错误边界接管。
  降到 720px：既覆盖 Virtuoso 的长度估算误差（实测约 380px），又不爆栈。

## R8 · 全站复检：窄屏的主角层级与两处空洞（2026-11-03）

### 假设

R0–R7 每一轮都盯一个新区域（首页 → 侧栏 → 列表页 → 设置 / 相册详情 →
阅读器），但**从来没有把八轮累积改动之后的所有页面放在一起看过一遍**。
累积的改动（舞台按视口高度收缩、键帽字号、右栏网格列数）可能互相打架，
也可能让某些断点的层级关系悄悄倒过来。本轮把 7 个页面 × 5 档断点 × 明暗
各拍一张（70 张），逐张看，假设：

1. **窄屏（≤1024）上"一屏一主角"是破的**：主角封面比次级封面还小 ——
   手机上主角封面只有 112×168，而"其余在读"的封面是 172×258，
   主角/次级比例 **0.65**（北极星要求 ≥1.6）。
2. **1024 档标题右侧有一大块空洞**：墙签列占满整行，标题右边空出约 355px。
3. 收藏页失效收藏的解释偏技术（"路径标识""标识会变"）。

### 备选方案（窄屏的主角层级怎么修）

| 方案 | 做法 | 结论 |

| A 只把手机的主角封面加大 | 封面 112 → 200，墙不动 | **否**：墙里的次级封面（172×258）仍然比主角大，层级照样倒过来 |

  - 封面 `w-[150px] md:w-[var(--stage-cover-w)]`（窄屏固定 150，md+ 跟随变量）。

### 审计工具自己的盲区（本轮最大的一块）

对比度审计原来的模型是"沿祖先链找背景，找到 background-image 就转像素通道"。
这条链有两个漏洞：

1. **压在图上的兄弟层看不见**：标签页 hero 的标题是一个 z-index 更高的
   兄弟节点，用负边距压在封面照片上，不在照片的 DOM 子树里 ——
   祖先链查不到，审计按"纯色底"判定，结论可能与实际相反。
2. **半透明角标判不准**：相册详情页右下角的页码角标是
   `bg-bg-elevated/85` 的半透明小块压在照片上。旧的模型要么按纯色算
   （忽略底下那张图），要么整块交给像素通道、让取样环跑到角标外面
   去采照片像素（把角标报成 2.59:1 这种假不合格）。

新的模型按**绘制顺序**判背板：

- 列出所有"图层"（`<img>` 与带 `background-image` 的元素）；
- 文字这一侧最上层的底 = 自己或最近的带背景的祖先（"蒙版"）；
- 找出与文字包围盒相交、且画在文字下面的图层；
- 两者里画得更上面的那个才是真正的背板：
  - 不透明底色 → 静态算得出，DOM 通道精确判；
  - 半透明底色 → 底下有图就交给像素通道，**取样落在底色那一层之内**；
  - 渐变 / `<img>` → 底色就是像素，交给像素通道。

自检也补了两类新样本（兄弟层、半透明角标），证明这套判据分得清好坏。

### 踩过的坑

1. **`elementsFromPoint` 不可用于找"画在下面"的东西**：

2. **图层对象漏了一个字段**：给图层加 `kind` 之前，`topmost()` 比较出来

   年份卡整片被判成白字压白底。**教训：判据对象要有完整字段，

3. **视口外的元素取到的是"透明"像素**：`getImageData` 越界返回全 0，

5. **半透明底色不等于纯色底色**：`bg-bg-elevated/85` 在暗色主题下是
   深色小块，在亮封面上是"深色小块 + 15% 的照片" ——

  - 缓存统计卡片的网格由 `grid-cols-2 sm:grid-cols-5`（视口断点）
    改成 `grid-cols-[repeat(auto-fit,minmax(112px,1fr))]`（容器断点）——
    **列数必须跟着容器走**：它在窄列里，屏幕再宽也不该挤成 5 列。
- **列表视图**（`AlbumGrid.tsx`）：≥1600px 加第三列。三列要每列
  ≥400px（缩略图 56 + 标题 200 + 计数 50 + 箭头 30 + 行内留白），
  也就是内容宽 ≥ 3×400 + 2×40 = 1280 → 视口 ≥ 1600。
- **首页右栏网格**（`global.css` + `HomeHeroes.tsx`）
  - 1024px 起改 5 列：这一档次级海报从 275px 压到 216px，
    主角/次级比例 1.19 → **1.52**；1440 档从 4 列改 5 列后
    比例 1.58 → **2.01**。
  - **条数上限从 React 挪进 CSS**，和列数写在同一处：
    列数与条数必须成对（4 列配 8 条、5 列配 10 条、6 列配 12 条），
    分两处维护就会出现"5 列只排 8 条、末行只剩 3 张"的半行。
    原来那两条 CSS 规则其实是**失效的** —— Tailwind 的 `hidden` 工具类
    在 utilities 层，压不过 components 层的 `display: block`。
- **审计工具**（`layout-audit.mjs` / `contrast-audit.mjs` / `test-e2e.ps1`）
  - 布局审计新增**有效内容宽**与**内容左缘**两个指标：容器宽度 ≠ 内容
    宽度（设置页的容器铺满、内容只有 768px 一列），只看容器宽度就
    永远发现不了居中窄列。
  - 新增**内容左缘对齐检查**：同一断点下所有页面的内容左缘必须落在
    同一条网格线上（阅读器是沉浸场景，不参与）。
  - 两个审计都新增**页面错误检测**：掉进错误边界的页面重试一次再判，
    仍失败就单独报出来 —— 崩掉的页面没有内容可量，报"全部通过"是假象。
  - 标签页审计**优先用真实标签**：真实库里有标签就用真的（e2e 的临时库
    就有：测试 / 空 格 / C++ / 100% …），没有才伪造，并在输出里写明。
  - `test-e2e.ps1 -Audit`：Playwright 跑完后，对同一个临时服务再跑一遍
    布局 / 对比度审计 —— 那里的临时媒体库带真实标签。

### 踩过的坑

1. **`.page-shell` 自带 `margin-inline: auto`**：光删掉 Tailwind 的
   `mx-auto` 没用 —— 居中是组件层写死的。真正的修法是**外层用全站
   的 shell、内层再限宽**，让"网格线"和"阅读行长"分成两件事。
2. **CSS 多列 + Tailwind 的断点类打架**：缓存卡片原本用
   `sm:grid-cols-5`（视口断点），在两列布局里屏幕很宽、容器很窄，
   5 张卡挤成两行断字。**列数要跟着容器走**（`auto-fit` + `minmax`）。
3. **CSS 里的 `display: block` 压不过 Tailwind 的 `hidden`**：
   层叠顺序是 utilities > components，原来那条"解除 8 条上限"的规则
   一直是失效的（直到把裁剪规则整个搬进 CSS 才真正生效）。
4. **审计的"内容宽度"量的是容器，不是内容**：设置页的容器铺满 1600px，
   实际内容只有 768px 一列 —— 不加"有效内容宽"这个指标就看不出。
5. **崩掉的页面会把审计带歪**：错误边界的居中块在 x=510，
   对齐检查把它当成"这一页偏右 282px"。崩掉的页面必须单独报，
   不能混进对齐比较里。

### 本轮之后仍未解决（下一轮待办）

- **相册详情页偶发爆栈**（`Maximum call stack size exceeded`）：
  react-virtuoso 的尺寸树是递归展开的，测量条目一多就爆栈。
  R7 把虚拟窗口下沿从 1600 降到 720 只是**降低**了概率，没有根治；
  实测在开发环境（StrictMode 双渲染）下能到 24/24，在生产构建下偶发。
  本轮先让审计能如实报出它（B48），根治另开一轮。
- 设置页在 1024 仍是单列（内容 768px 铺满主区）—— 这一档没有第二列
  的空间，两列会让服务端的路径输入框窄到读不全。
- 首页右栏在 1799px 档的比例 1.63（比 1440 档低）：右栏变宽，
  5 列的每列也跟着变宽。次级海报的比例随视口漂移，规则只能给区间。
- 标签页的字段规则（标签名超长、特殊字符）目前只有 e2e 的功能覆盖，
